# 010 · 路径沙箱：为什么「字符串前缀匹配」一定会出事

## 落地决定

1. **越界判定用 `path.relative`，不用 `startsWith`。**
   经典漏洞：工作区 `C:\ws`、目标 `C:\ws2\x`——`startsWith` 会放行。
   本项目的用例专门造了 `ws` 与 `ws2` 同前缀的目录来锁死这一点。

2. **必须先逐条拒绝 Windows 特有的绕过手法**，再谈边界：

   | 手法 | 例子 | 为什么危险 |
   |------|------|-----------|
   | 设备路径 | `\\?\C:\Windows\x` | 绕过 Win32 路径规范化，`..` 不再被解析 |
   | UNC | `\\server\share\x` | 直接访问网络位置 |
   | 备用数据流 | `file.txt:hidden` | 隐藏数据、绕过文件长度检查 |
   | 尾随点/空格 | `secret.txt.` | 系统会静默剥离，等价于 `secret.txt` |
   | 保留设备名 | `CON` / `NUL` / `COM1` | 写向设备而非文件 |

   这些检查必须针对**原始输入**做——先 `trim()` 会把尾随空格吃掉，等于把这道防线自己拆了。

3. **`..` 不能当成「可疑片段」拦掉。**
   首版把 `..` 命中了「以点结尾」规则，结果 `sub/../a.txt`（完全在工作区内）被误拒。
   正确做法：`..` 与 `.` 是路径语义符号，越界与否**只由最终的 relative 判定**。
   「宁缺勿滥」不等于「宁可误杀」——过度拦截会逼用户关掉防护。

4. **字符串校验不够，必须校验真实路径（realpath）。**
   攻击面：在工作区内建一个 junction / symlink 指向用户目录下的敏感文件，
   上述所有字符串检查都会通过。做法：从目标向上找第一个**已存在**的祖先做 realpath，
   判断其真实位置仍在工作区内；这样既能拦软链逃逸，又不会误伤「待创建文件」的写场景。

5. **fail closed，且错误要能解释。**
   工作区根目录都不存在、realpath 反复失败等不确定情况一律拒绝；
   错误信息写明「拒绝了什么、为什么」，用户才可能理解并修正，而不是以为程序坏了。

## 边界与取舍

- 本层只解决「路径不能越界」；「命令能不能跑」属 W5 高危命令清单，二者不可互相替代。
- 大小写：Windows 下比较时统一转小写，否则 `C:\WS` 与 `c:\ws` 会被判为不同目录。
- 8.3 短名（如 `PROGRA~1`）未单独拦截：它仍会走 relative 判定，越界会被拦；
  如需更严，可在 realpath 之后再用系统原生 realpath 比对一次。
