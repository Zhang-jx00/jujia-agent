# F2: Multi-agent and sub-agent orchestration

## Findings

### [1] Claude Code subagents are specialized assistants that run in their own context window with a custom system prompt, restricted tools, and independent permissions; the parent delegates matching tasks and receives only a summary.
- quote: "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions. When Claude encounters a task that matches a subagent's description, it delegates to that subagent, which works independently and returns results."
- url: https://code.claude.com/docs/en/sub-agents
- source_type: primary
- published: unknown (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: implement role templates (explore/review/research/test/build) as declarative files: name + routing description + tools allowlist + model + system prompt; parent routes by description match and consumes summaries only.

### [2] Claude Code ships built-in role-specialized subagents Explore (read-only, thoroughness quick/medium/very thorough), Plan (read-only planning research), and General-purpose (exploration + modification); Explore/Plan deny Write and Edit to keep research cheap and non-mutating.
- quote: "Explore: A fast, read-only agent optimized for searching and analyzing codebases. ... Tools: read-only tools; Write and Edit are denied. ... When invoking Explore, Claude specifies a thoroughness level: quick for targeted lookups, medium for balanced exploration, or very thorough for comprehensive analysis."
- url: https://code.claude.com/docs/en/sub-agents
- source_type: primary
- published: unknown (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: enforce tool ACLs at spawn time, not by prompt alone; give explore agents a thoroughness parameter so the primary can buy more depth only when needed.

### [3] Claude Code subagent frontmatter supports isolation: worktree, which runs the subagent inside a temporary git worktree branched from the default branch (not parent HEAD) and auto-cleans if no changes were made; commands that escape the worktree are blocked.
- quote: "Set to `worktree` to run the subagent in a temporary git worktree, giving it an isolated copy of the repository branched by default from your default branch rather than the parent session's `HEAD`. The worktree is automatically cleaned up if the subagent makes no changes."
- url: https://code.claude.com/docs/en/sub-agents
- source_type: primary
- published: unknown (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: for parallel build/test agents on Windows, implement per-agent git worktree isolation with CWD enforcement + command screening; discard worktrees that produced no diffs.

### [4] Claude Code budget-controls multi-agent prompt context: combined non-built-in subagent descriptions over 15,000 tokens trigger a startup warning; detail should move into system prompts that load only when that subagent runs.
- quote: "When the combined descriptions of your subagents, except the built-in ones, exceed 15,000 tokens, Claude Code shows a warning at startup with the total token count. Trim the `description` fields of your subagents, and move detail into each subagent's system prompt, which only loads when that subagent runs."
- url: https://code.claude.com/docs/en/sub-agents
- source_type: primary
- published: unknown (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: keep routing metadata tiny (name + 1-line trigger); put long role instructions behind the router so primary-agent context stays small as roles grow.

### [5] Anthropic Research production multi-agent system uses an orchestrator-worker pattern: LeadResearcher plans, saves plan to Memory, spawns specialized subagents in parallel, synthesizes, optionally spawns more, then hands off to a CitationAgent.
- quote: "Our Research system uses a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel. ... The LeadResearcher begins by thinking through the approach and saving its plan to Memory to persist the context ... Once sufficient information is gathered, the system exits the research loop and passes all findings to a CitationAgent."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high
- desktop-agent takeaway: primary agent = planner + synthesizer + citation/verifier stage; workers never own the final user answer; persist the plan outside the context window before fan-out.

### [6] Anthropic measured that a multi-agent research system (Claude Opus 4 lead + Claude Sonnet 4 subagents) outperformed single-agent Claude Opus 4 by 90.2% on their internal research eval, but multi-agent systems use ~15× more tokens than chat while single agents use ~4×.
- quote: "We found that a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval. ... In our data, agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high
- desktop-agent takeaway: use expensive multi-agent paths only for high-value/open-ended tasks; cheaper single-agent or explore-only paths for routine coding; surface token cost estimates in the desktop UI.

### [7] Anthropic found three factors explained 95% of BrowseComp performance variance: token usage alone explained 80%, with tool-call count and model choice as the other two; coding tasks were called a poorer fit for multi-agent because they have fewer truly parallelizable pieces.
- quote: "In our analysis, three factors explained 95% of the performance variance in the BrowseComp evaluation ... token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors. ... most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high
- desktop-agent takeaway: for coding, prefer role-specialized sequential/semi-parallel workflows over pure swarm; measure token budget and tool-call counts as first-class quality/cost metrics.

### [8] Anthropic encodes effort-to-complexity scaling in prompts: simple fact-finding ~1 agent / 3–10 tool calls; direct comparisons 2–4 subagents / 10–15 calls each; complex research can use >10 subagents; early failure modes included spawning 50 subagents for simple queries.
- quote: "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities. ... Early agents made errors like spawning 50 subagents for simple queries."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high
- desktop-agent takeaway: hard-cap concurrency slots by task class; primary must estimate complexity before spawn; refuse/warn when subagent count exceeds an explicit budget.

### [9] Anthropic parallelized both lead-level spawn (3–5 subagents concurrently) and worker-level tool calls (3+ tools in parallel), cutting complex research time by up to 90%; production lead agents still executed subagents synchronously, which bottlenecks steering and coordination.
- quote: "Our early agents executed sequential searches, which was painfully slow. For speed, we introduced two kinds of parallelization: (1) the lead agent spins up 3-5 subagents in parallel rather than serially; (2) the subagents use 3+ tools in parallel. These changes cut research time by up to 90% ... Currently, our lead agents execute subagents synchronously, waiting for each set of subagents to complete before proceeding."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high
- desktop-agent takeaway: implement a concurrency-slot pool (default ~3–5) + intra-agent tool fan-out; start with barrier-style sync for reliability, design message bus for later async steering.

### [10] Anthropic recommends filesystem/artifact handoff over “game of telephone”: subagents persist work externally and return lightweight references to the coordinator, reducing information loss and token overhead for structured outputs.
- quote: "Rather than requiring subagents to communicate everything through the lead agent, implement artifact systems where specialized agents can create outputs that persist independently. Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator."
- url: https://www.anthropic.com/engineering/built-multi-agent-research-system
- source_type: primary
- published: 2025-06-13
- confidence: high
- desktop-agent takeaway: for a TypeScript+Electron agent, write worker outputs to a shared workspace (findings/, patches/, test logs) and return paths+hashes to the primary, not full transcripts.

### [11] OpenAI Swarm defines multi-agent orchestration via two primitives—Agent (instructions + tools) and handoffs—where a tool returning another Agent transfers control; Swarm is educational/stateless and is officially replaced by the OpenAI Agents SDK.
- quote: "It accomplishes this through two primitive abstractions: `Agent`s and handoffs. An `Agent` encompasses `instructions` and `tools`, and can at any point choose to hand off a conversation to another `Agent`. ... Swarm is now replaced by the OpenAI Agents SDK, which is a production-ready evolution of Swarm."
- url: https://github.com/openai/swarm
- source_type: primary
- published: unknown (repo current as of 2026; educational)
- confidence: high
- desktop-agent takeaway: model handoff as “tool call returns next agent identity + optional context”; keep the run loop outside the LLM so routing is inspectable/testable.

### [12] OpenAI Agents SDK distinguishes two production coordination patterns: agents-as-tools (manager keeps the conversation, specialist called via Agent.as_tool for bounded subtasks) vs handoffs (triage routes and specialist becomes the active agent for the rest of the turn); it also ships Sandbox agents that run specialists in real isolated workspaces.
- quote: "Agents as tools: A manager agent keeps control of the conversation and calls specialist agents through `Agent.as_tool()`. ... Handoffs: A triage agent routes the conversation to a specialist, and that specialist becomes the active agent for the rest of the turn. ... Sandbox agents: Run specialists inside real isolated workspaces."
- url: https://openai.github.io/openai-agents-python/multi_agent/
- source_type: primary
- published: unknown (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: coding-desktop design: use agents-as-tools for explore/review/test helpers that must not own the user thread; use handoff only when a specialist should drive the rest of the turn; isolate sandbox/build agents in worktrees/containers.

### [13] OpenAI Agents SDK handoffs are presented to the LLM as tools named transfer_to_<agent_name>; handoff() supports on_handoff callbacks, input_type metadata schemas, input filters that rewrite history for the next agent, and recommended prompt prefixes so models know how to use handoffs.
- quote: "Handoffs are represented as tools to the LLM. So if there's a handoff to an agent named `Refund Agent`, the tool would be named `transfer_to_refund_agent`. ... `input_filter`: This lets you filter the input received by the next agent."
- url: https://openai.github.io/openai-agents-python/handoffs/
- source_type: primary
- published: unknown (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: standardize handoff tool names and structured metadata (reason, priority, summary); implement history filters so subagents don't inherit full parent transcript cost.

### [14] Microsoft AutoGen AgentChat provides named multi-agent team patterns (Selector Group Chat, Swarm, Magentic-One, GraphFlow workflows) on top of autogen-core event-driven runtime; Core documents design patterns including Concurrent Agents, Sequential Workflow, Group Chat, Handoffs, Mixture of Agents, Multi-Agent Debate, Reflection, and Code Execution.
- quote: "AgentChat provides intuitive defaults, such as Agents with preset behaviors and Teams with predefined multi-agent design patterns. ... Multi-Agent Design Patterns: Concurrent Agents, Sequential Workflow, Group Chat, Handoffs, Mixture of Agents, Multi-Agent Debate, Reflection, Code Execution."
- url: https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/index.html
- source_type: primary
- published: © 2024 Microsoft (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: treat these as a pattern catalog to implement, not a library dependency for Windows Electron; map GraphFlow→typed workflow graph, Magentic-One→orchestrator with stall/reset budgets.

### [15] AutoGen's Handoff pattern (originally from OpenAI Swarm) is implemented in Core via pub-sub delegate tools: a tool call returns another agent's topic type, the current agent publishes UserTask to that topic, and the delegate agent adopts persona immediately; advantages listed are distributed runtime, bring-your-own agent, and natively async APIs.
- quote: "Handoff is a multi-agent design pattern introduced by OpenAI in an experimental project called Swarm. The key idea is to let agent delegate tasks to other agents using a special tool call. ... If the response contains a handoff tool call, the agent delegates the task to another agent by publishing a UserTask message to the topic specified in the tool call result."
- url: https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/handoffs.html
- source_type: primary
- published: © 2024 Microsoft
- confidence: high
- desktop-agent takeaway: separate ordinary tools from delegate tools in the TypeScript agent; delegate = emit typed message to topic/mailbox, not recursive in-process function call—this is how Claude Code teams/mailbox also work.

### [16] AutoGen Concurrent Agents documents three concurrency patterns—single message / multiple processors (broadcast topic), multiple messages / multiple processors (topic-routed), and direct messaging—where a DelegatorAgent fans out subtasks to distinct WorkerAgent AgentIds via asyncio.gather and combines results.
- quote: "worker1_result, worker2_result = await asyncio.gather(self.send_message(subtask1, self.worker_instances[0]), self.send_message(subtask2, self.worker_instances[1])) ... combined_result = f\"Part 1: {worker1_result.result}, Part 2: {worker2_result.result}\"."
- url: https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/concurrent-agents.html
- source_type: primary
- published: © 2024 Microsoft
- confidence: high
- desktop-agent takeaway: address workers by AgentId (type+key) so N instances of one worker class can run concurrently; implement fan-out/join (ALL/ANY) in the primary, not inside workers.

### [17] CrewAI Crews use sequential (default) or hierarchical process; hierarchical requires manager_llm or manager_agent that coordinates and validates; crew-level max_rpm caps request rate and overrides per-agent settings; checkpointing can save after task_completed for resume via Crew.from_checkpoint.
- quote: "Process (optional) | The process flow (e.g., sequential, hierarchical) the crew follows. Default is sequential. ... Manager LLM (optional) | The language model used by the manager agent in a hierarchical process. Required when using a hierarchical process. ... Max RPM (optional) | Maximum requests per minute the crew adheres to during execution."
- url: https://docs.crewai.com/en/concepts/crews
- source_type: primary
- published: unknown (docs current as of 2026)
- confidence: high
- desktop-agent takeaway: implement both sequential pipeline (explore→build→test→review) and hierarchical mode with explicit manager; enforce RPM/concurrency as a global resource governor on the Electron main process.

### [18] Claude Code experimental Agent Teams (CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1) coordinate multiple full sessions: team lead + independent teammates, shared task list with pending/in_progress/completed and task dependencies, mailbox JSON files under ~/.claude/teams/{team-name}/inboxes/, and file-locked task claims to prevent races.
- quote: "Agent teams let you coordinate multiple Claude Code instances working together. One session acts as the team lead ... Task claiming uses file locking to prevent race conditions when multiple teammates try to claim the same task simultaneously. ... Each agent's mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`."
- url: https://code.claude.com/docs/en/agent-teams
- source_type: primary
- published: unknown (docs describe v2.1.178+; experimental)
- confidence: high
- desktop-agent takeaway: a desktop multi-agent UI can mirror this: lead session + per-teammate transcripts, shared Task tool board with dependency unblocking, and file/mailbox IPC; recommended team size 3–5; no nested teams; token cost scales linearly with teammates.

### [19] A2A (Agent2Agent) Protocol is an open standard for agent-to-agent interoperability using HTTP, JSON-RPC, and SSE; it explicitly is NOT a sub-agent/tool-call protocol—MCP is agent-to-tool, A2A is agent-to-agent; agents are discovered via Agent Card (e.g. /.well-known/agent-card) then messaged via sendMessage / sendMessageStream; originally developed by Google and donated to the Linux Foundation, v1.0 under Apache 2.0.
- quote: "Not a sub-agent or tool-call protocol. A2A does not specify how an agent talks to its own sub-agents or how it invokes tools — use your framework's native primitives, or MCP, for those. ... MCP is for agent-to-tool communication ... A2A is for agent-to-agent communication. ... A2A was originally developed by Google and donated to the Linux Foundation."
- url: https://a2a-protocol.org/latest/ and https://a2a-protocol.org/latest/topics/what-is-a2a/
- source_type: primary
- published: unknown (site current 2026; blog note 2026-08-27 A2A joins Agentic AI Foundation)
- confidence: high
- desktop-agent takeaway: for 俱佳Agent, internal primary/sub agents need native tool/mailbox protocol (not A2A); reserve A2A for optional external remote-agent integration; pair with MCP for tool access. SDKs exist for Python, JS/TS, Java, .NET, Go, Rust (TS relevant for Electron).

### [20] Microsoft is migrating AutoGen to Microsoft Agent Framework: AutoGen pioneered GroupChat and event-driven runtime; Agent Framework centers multi-agent orchestration on a typed, graph-based Workflow (data-flow edges, agents/functions/sub-workflows as executors) vs AutoGen GraphFlow control-flow/broadcast; agent-as-tool and Magentic-style orchestrators are first-class; distributed runtime planned but currently single-process focused.
- quote: "Microsoft Agent Framework is a new multi-language SDK for building AI agents and workflows using LLMs. It represents a significant evolution of the ideas pioneered in AutoGen ... Agent Framework centers on a typed, graph-based Workflow that routes data along edges and activates executors when inputs are ready. ... Agent Framework focuses on single-process composition today; distributed execution is planned."
- url: https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-autogen/
- source_type: primary
- published: ms.date 2026-04-01 (updated 2026-08-25)
- confidence: high
- desktop-agent takeaway: prefer data-flow workflow graphs over pure message-broadcast for coding pipelines; if calling Python multi-agent stacks from TypeScript, target Agent Framework rather than new AutoGen designs; implement Magentic-style max_round/max_stall/max_reset guards.
