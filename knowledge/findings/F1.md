# F1: Agent core mechanisms and design patterns

## Findings

### [1] ReAct interleaves free-text reasoning traces with task-specific actions so the model can plan, update, and recover while gathering external evidence.
- quote: "we explore the use of LLMs to generate both reasoning traces and task-specific actions in an interleaved manner, allowing for greater synergy between the two: reasoning traces help the model induce, track, and update action plans as well as handle exceptions, while actions allow it to interface with external sources"
- url: https://arxiv.org/abs/2210.03629
- source_type: primary
- published: 2022-10-06 (v1); 2023-03-10 (v3, ICLR camera-ready)
- confidence: high
- **What it is**: Academic foundation of the think-then-act agent pattern (Reason+Act).
- **Why it matters for a desktop agent**: Justifies a loop that emits both plan text and tool calls each step, not silent action-only steps.
- **Implementation takeaway**: Persist reasoning traces alongside tool I/O in the transcript so users can audit plan changes; ReAct beat imitation/RL baselines by 34%/10% absolute success on ALFWorld/WebShop with only 1–2 in-context examples.

### [2] The OpenAI Agents SDK agent loop is a three-way branch on each model turn: final output ends the run, handoff switches agents, tool calls execute and re-enter the loop.
- quote: "1. We call the LLM for the current agent, with the current input. 2. The LLM produces its output. 1. If the runner classifies the LLM's output as final output, the loop ends... 2. If the LLM requests a handoff, we update the current agent and input, and re-run the loop. 3. If the LLM produces tool calls, we run those tool calls, append the results, and re-run the loop."
- url: https://openai.github.io/openai-agents-python/running_agents/
- source_type: primary
- published: unknown (current SDK docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Canonical production agent-loop control flow.
- **Why it matters for a desktop agent**: A TypeScript+Electron agent can mirror this Runner structure without inventing novel control flow.
- **Implementation takeaway**: Final output = text with desired type and **no tool calls**; cap loops with `max_turns` (SDK raises `MaxTurnsExceeded`); `max_turns=None` disables the limit.

### [3] Anthropic distinguishes workflows (LLM orchestrated on predefined code paths) from agents (LLM dynamically directs process and tool usage), and recommends the simplest system that works.
- quote: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks."
- url: https://www.anthropic.com/engineering/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high
- **What it is**: Architectural taxonomy plus guidance: start simple, add agentic complexity only when demonstrated outcomes improve.
- **Why it matters for a desktop agent**: Most learning tasks do not need a fully autonomous loop; plan-execute pipelines may be more reliable.
- **Implementation takeaway**: Implement composable workflows first (prompt chaining with gates, routing, parallelization, orchestrator-workers, evaluator-optimizer), then graduate to a free-form tool loop for open-ended coding tasks.

### [4] Coding agents are a first-class agentic domain because solutions are test-verifiable and agents can iterate on test feedback; human review remains required for broader requirements.
- quote: "Code solutions are verifiable through automated tests; Agents can iterate on solutions using test results as feedback; the problem space is well-defined and structured; and output quality can be measured objectively."
- url: https://www.anthropic.com/engineering/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high
- **What it is**: Goal-verification rationale for coding agents.
- **Why it matters for a desktop agent**: Builds a concrete stop/reward signal into the agent loop (tests green = done candidate).
- **Implementation takeaway**: After edits, always run project tests/linters; treat test results as environment ground truth each step; do not claim completion without automated verification.

### [5] Evaluator-optimizer is Anthropic's named workflow pattern for goal verification: one LLM generates, another evaluates against criteria, looping until the evaluator accepts.
- quote: "In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop... The two signs of good fit are, first, that LLM responses can be demonstrably improved when a human articulates their feedback; and second, that the LLM can provide such feedback."
- url: https://www.anthropic.com/engineering/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high
- **What it is**: Explicit plan-verify-revise loop pattern.
- **Why it matters for a desktop agent**: Separates "do" from "check" so goal verification is not self-certified by the same context.
- **Implementation takeaway**: Spawn a separate evaluator agent (or model) with a rubric (acceptance criteria, test output, user constraints) that can reject and re-enter generation.

### [6] Tool designs should be treated as agent-computer interfaces: Anthropic's SWE-bench agent spent more time optimizing tools than prompts and switched file edits to absolute paths after relative-path failures.
- quote: "While building our agent for SWE-bench, we actually spent more time optimizing our tools than the overall prompt. For example, we found that the model would make mistakes with tools using relative filepaths after the agent had moved out of the root directory. To fix this, we changed the tool to always require absolute filepaths—and we found that the model used this method flawlessly."
- url: https://www.anthropic.com/engineering/building-effective-agents
- source_type: primary
- published: 2024-12-19
- confidence: high
- **What it is**: Tool-calling design principle (ACI) and concrete failure recovery lesson.
- **Why it matters for a desktop agent**: Path/root issues are the most common desktop coding-agent bug class.
- **Implementation takeaway**: Require absolute Windows paths in tool schemas; avoid formats that need the model to count lines or escape JSON for code; "poka-yoke" tool args; give models tokens to think before irreversible formats.

### [7] Toolformer shows LMs can self-supervise tool-use decisions: when to call, which API, what args, and how to incorporate results—using only a handful of demos per API.
- quote: "We introduce Toolformer, a model trained to decide which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results into future token prediction. This is done in a self-supervised way, requiring nothing more than a handful of demonstrations for each API."
- url: https://arxiv.org/abs/2302.04761
- source_type: primary
- published: 2023-02-09
- confidence: high
- **What it is**: Academic basis for tool selection/integration as learned behavior (calculator, QA, search, translation, calendar).
- **Why it matters for a desktop agent**: Modern APIs already emit tool-call tokens; your harness still must define tools so "when/how to call" is unambiguous.
- **Implementation takeaway**: Provide few-shot tool usage examples in system prompts; include calculator/search/shell style primitives; validate that results are re-injected as tokens the model can condition on next.

### [8] Claude Agent SDK defines a 5-step loop ending when the model produces a response with no tool calls; a coding fix of failing tests spans multiple turns of Bash/Read/Edit then a final text-only result.
- quote: "Claude continues calling tools and processing results until it produces a response with no tool calls... Turn 1: Claude calls Bash to run npm test... Turn 3: Claude calls Edit to fix auth.ts... Final turn: Claude produces a text-only response with no tool calls: \"Fixed the auth bug, all three tests pass now.\""
- url: https://code.claude.com/docs/en/agent-sdk/agent-loop
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Production agent-loop lifecycle, message types (`SystemMessage` init/compact_boundary, `AssistantMessage`, `UserMessage`, `ResultMessage`), turn semantics.
- **Why it matters for a desktop agent**: Message-stream architecture maps directly to an Electron IPC stream UI.
- **Implementation takeaway**: One turn = tool calls + automatic re-feed; expose `ResultMessage.subtype` (`success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`); gate dangerous tools with permission modes (`default`, `acceptEdits`, `plan`, `dontAsk`, `auto`, `bypassPermissions`).

### [9] Parallel tool execution must be constrained by mutability: read-only tools may run concurrently; state-mutating tools run sequentially.
- quote: "Read-only tools (like Read, Glob, Grep, and MCP tools marked as read-only) can run concurrently. Tools that modify state (like Edit, Write, and Bash) run sequentially to avoid conflicts."
- url: https://code.claude.com/docs/en/agent-sdk/agent-loop
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Concrete concurrency policy for multi-tool turns.
- **Why it matters for a desktop agent**: Parallel file edits on Windows will race and corrupt workspaces.
- **Implementation takeaway**: Tag each tool `readOnlyHint`; OpenAI SDK analogously exposes `tool_execution.max_function_tool_concurrency` vs provider-side `parallel_tool_calls`.

### [10] Long single-context coding agents suffer agentic laziness, self-preferential bias, and goal drift; dynamic multi-agent harnesses exist to combat these failure modes.
- quote: "Agentic laziness refers to when Claude stops before finishing a particularly complex, multi-part task... Self-preferential bias refers to Claude's tendency to prefer its own results... Goal drift refers to the gradual loss of fidelity to the original objective across many turns, especially after compaction."
- url: https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code
- source_type: primary
- published: 2026-06-02
- confidence: high
- **What it is**: Named failure modes + dynamic workflow patterns (classify-and-act, fan-out-and-synthesize, adversarial verification, tournament, loop-until-done).
- **Why it matters for a desktop agent**: Failure recovery must include external verification, not only more tool retries.
- **Implementation takeaway**: Use independent verifier agents / worktrees; pair workflows with hard completion conditions (`/goal`); budget tokens explicitly; resume interrupted workflows from checkpoints.

### [11] Context engineering optimizes a finite "attention budget": good agent context is the smallest high-signal token set, maintained via compaction, structured note-taking, and sub-agent isolation.
- quote: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome... Compaction... Structured note-taking... Sub-agent architectures... each subagent... returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)."
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: primary
- published: 2025-09-29
- confidence: high
- **What it is**: Modern context-engineering doctrine (context rot, just-in-time retrieval, hybrid CLAUDE.md + glob/grep pattern).
- **Why it matters for a desktop agent**: Electron agents accumulate multi-hour coding sessions; context is the primary reliability bottleneck.
- **Implementation takeaway**: Auto-compact near window limits; persist NOTES/todo outside the window; use subagents that return short summaries; store lightweight identifiers (paths) and load tool results just-in-time; clear old tool outputs; keep persistent rules in re-injected memory files, not one-shot prompts.

### [12] LangGraph is a low-level orchestration runtime that mixes deterministic hand-coded steps with LLM-driven steps in one graph, with persistence, interrupts, and durable long-running execution.
- quote: "LangGraph gives you fine-grained control to mix deterministic, hand-coded steps with LLM-driven agentic steps in the same graph... LangGraph is focused on the underlying capabilities important for agent orchestration: durable execution, streaming, human-in-the-loop, and more."
- url: https://docs.langchain.com/oss/python/langgraph/overview
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: State-machine/graph model for agents (inspired by Pregel/Apache Beam/NetworkX); API surface is `StateGraph`, nodes, edges, `START`/`END`.
- **Why it matters for a desktop agent**: Plan-execute and permission gates fit explicit state machines better than free-form loops alone.
- **Implementation takeaway**: Model agent states as a graph with typed state; put reliability-critical steps (apply patch, run tests, human approve) as deterministic nodes; use interrupts for HITL; persist checkpoints to resume after crashes.

### [13] OpenAI Agents SDK productionizes tool calling into five categories (hosted, local runtime, FunctionTool, agents-as-tools, experimental Codex) plus error-recovery knobs that return tool-not-found failures to the model instead of crashing.
- quote: "By default, if the model emits a function tool call that does not match any function tool available to the current agent, the runner raises ModelBehaviorError. Set tool_not_found_behavior=\"return_error_to_model\" when you want the run to remain recoverable. In that mode, the SDK appends a function_call_output for the unresolved tool call and runs the model again"
- url: https://openai.github.io/openai-agents-python/tools/ and https://openai.github.io/openai-agents-python/running_agents/
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Tool taxonomy + structured failure recovery inside the loop.
- **Why it matters for a desktop agent**: Models hallucinate tool names; recoverable error feedback is better than hard abort.
- **Implementation takeaway**: Implement `error_handlers` for `max_turns`, `model_refusal`, `invalid_final_output`; optionally return model-visible tool errors; support `Agent.as_tool()` for nested subagents; use deferred tool search/namespaces when the tool surface is large (keep namespaces ideally <10 functions).

### [14] AutoGen frames agents as customizable conversational participants that can combine LLMs, human inputs, and tools under flexible multi-agent conversation patterns programmed in NL or code.
- quote: "AutoGen agents are customizable, conversable, and can operate in various modes that employ combinations of LLMs, human inputs, and tools... Both natural language and computer code can be used to program flexible conversation patterns for different applications."
- url: https://arxiv.org/abs/2308.08155
- source_type: primary
- published: 2023-08-16 (v1); 2023-10-03 (v2)
- confidence: high
- **What it is**: Multi-agent conversation framework (Microsoft Research) for coding, math, QA, OR, entertainment.
- **Why it matters for a desktop agent**: Multi-step reasoning can be modeled as agent↔agent dialogues, not only a single agent + tools.
- **Implementation takeaway**: For learning products, a teacher agent + executor agent + critic agent conversation is a validated pattern; human input is a first-class message source in the loop.
