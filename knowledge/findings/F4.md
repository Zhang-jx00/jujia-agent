# F4: Memory management and context

## Findings

### [1] Hierarchical virtual context management (MemGPT) is the foundational pattern for short-term vs long-term agent memory
- quote: "we propose virtual context management, a technique drawing inspiration from hierarchical memory systems in traditional operating systems that provide the appearance of large memory resources through data movement between fast and slow memory... MemGPT... intelligently manages different memory tiers... and utilizes interrupts to manage control flow"
- url: https://arxiv.org/abs/2310.08560
- source_type: paper (arXiv:2310.08560, Packer et al.; core of Letta)
- published: 2023-10-12 (v2 2024-02-12)
- confidence: high
- implementation: Treat main context as "fast RAM" and a durable local store as "disk". Implement agent-triggered paging (read/write tools) rather than always stuffing history into the prompt. Interrupts/compaction events re-route control between agent and memory manager.

### [2] Long-term memory enables multi-session agents that "remember, reflect, and evolve"
- quote: "document analysis, where MemGPT is able to analyze large documents that far exceed the underlying LLM's context window, and multi-session chat, where MemGPT can create conversational agents that remember, reflect, and evolve dynamically through long-term interactions with their users"
- url: https://arxiv.org/abs/2310.08560
- source_type: paper
- published: 2023-10
- confidence: high
- implementation: Separate "session memory" (current turn buffer) from "user/agent long-term memory" that accumulates across sessions. For 俱佳Agent: persist per-user identity + preferences beyond chat transcripts; allow the agent tools to revise them (reflect).

### [3] Letta/MemGPT production model: memory blocks pinned in system prompt + full-state DB persistence + archival retrieval after eviction
- quote: "all state, includes memories, user messages, reasoning, tool calls, are all persisted in a database, so they are never lost, even once evicted from the context window. Important 'core' memories are injected into the context window of the LLM, and the agent can modify its own memories through tools."
- url: https://docs.letta.com/guides/agents/memory
- source_type: official product docs (Letta, f.k.a. MemGPT)
- published: current docs (accessed 2026-09-18)
- confidence: high
- implementation: Three tiers for Electron agent: (1) core/pinned blocks always in system prompt; (2) in-context message window; (3) archival passages searchable after compaction. Eviction must never mean deletion—write every message/tool result to disk first.

### [4] Memory blocks are editable, attachable, shareable units of context (semantic core + episodic archive separation)
- quote: "Memory (organized into blocks) are pieces of context (strings) that are editable by agents via memory tools... Memory blocks that are attached to an agent are in-context (pinned to the system prompt). Memory blocks can be attached to multiple agents at once ('shared blocks')."
- url: https://docs.letta.com/guides/agents/memory
- source_type: official product docs
- published: current docs
- confidence: high
- implementation: Implement semantic memory as named blocks (persona, preferences, learning goals, project state) with agent write tools + human edit path. Shared blocks enable multi-agent or multi-session handoff. Episodic memory lives in the message/archival store, not in pinned blocks.

### [5] Session vs conversation separation enables concurrent handoff and forkable threads
- quote: "Conversations: Independent message threads with the same underlying agent, allows for easy concurrent messaging between a single agent and many different users." Also: Runs contain many Steps; Messages remain retrievable via API after compaction.
- url: https://docs.letta.com/guides/agents/memory
- source_type: official product docs
- published: current docs
- confidence: high
- implementation: Agent identity (long-term memory) ≠ session thread (episodic). Design data model: `agent_id` → memory blocks + tools; `session_id`/`conversation_id` → message list. Conversation fork/API compact endpoints are the pattern for handoff and restarts.

### [6] Context window budgets: treat context as a finite "attention budget" with diminishing returns (context rot)
- quote: "Context, therefore, must be treated as a finite resource with diminishing marginal returns... LLMs have an 'attention budget'... Every new token introduced depletes this budget... find the *smallest possible* set of high-signal tokens that maximize the likelihood of some desired outcome."
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: official vendor engineering guide (Anthropic Applied AI)
- published: 2025-09-29
- confidence: high
- implementation: Hard budget for 俱佳Agent assembly: system+core memory (~fixed), tools schema (cap), retrieved memories (k limit), recent turns (sliding window), reserved reply headroom. Prefer curated high-signal snippets over full transcripts. Monitor utilization; trigger compaction at e.g. 70–80% of model window.

### [7] Compaction: summarize + reinitiate context; preserve decisions/bugs; clear tool outputs first
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: official vendor engineering guide
- published: 2025-09-29
- confidence: high
- implementation: Two-stage compression: (1) zero-loss tool-result clearing of old tool payloads once digested; (2) LLM summarization into a structured handoff packet (goals, decisions, open bugs, file paths, next actions) + keep last N raw turns. Tune compaction prompt for recall first, then precision.

### [8] Structured note-taking / agentic memory (file-based) is the practical long-horizon memory outside context
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: official vendor engineering guide
- published: 2025-09-29
- confidence: high
- implementation: Give the agent tools: `memory_write(path, content)`, `memory_read`, `memory_search`. Notes (NOTES.md / session summaries) are the cheapest production pattern. For Windows Electron: **atomic writes** (write temp + fsync + rename), crash-safe under concurrent sessions; schema-versioned `memory.json` for structured fields + markdown notes for freeform.

### [9] Just-in-time retrieval + hybrid context (identifiers in prompt, load on demand) beats stuffing everything up front
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: official vendor engineering guide
- published: 2025-09-29
- confidence: high
- implementation: Pin only a short memory index/TOC; agent resolves IDs via search tools. Progressive disclosure: metadata (path, mtime, tags) signals relevance without loading bodies. Hybrid: always inject core profile + session summary; pull episodic/vector hits on demand.

### [10] RAG alone is static; agent memory needs dynamic extraction + consolidation from conversations
- quote: "existing retrieval-augmented generation (RAG) frameworks for large language model (LLM)-based agents are limited to static document retrieval, enterprise applications demand dynamic knowledge integration from diverse sources including ongoing conversations and business data... Zep addresses this... through its core component Graphiti -- a temporally-aware knowledge graph engine"
- url: https://arxiv.org/abs/2501.13956
- source_type: paper (arXiv:2501.13956, Zep)
- published: 2025-01-20
- confidence: medium-high
- implementation: RAG = document/chunk retrieval. Agent memory = write-path extraction (what changed about the user/task) + update/consolidate + temporal validity. For personal learning agent: use RAG for course/docs; use memory layer for "user prefers X / completed Y / stuck on Z".

### [11] Mem0: production memory architecture extracts, consolidates, retrieves; graph variant adds relations; large cost/latency wins vs full context
- quote: "Mem0, a scalable memory-centric architecture... dynamically extracting, consolidating, and retrieving salient information from ongoing conversations... enhanced variant that leverages graph-based memory representations... Mem0 achieves 26% relative improvements in the LLM-as-a-Judge metric over OpenAI... Mem0 attains a 91% lower p95 latency and saves more than 90% token cost [vs full-context]"
- url: https://arxiv.org/abs/2504.19413
- source_type: paper (arXiv:2504.19413, Mem0)
- published: 2025-04-28
- confidence: high
- implementation: Memory write pipeline: ingest turn → LLM extract candidate facts → dedupe/merge/update against existing store (ADD/UPDATE/DELETE/NOOP) → embed+persist. Read path: retrieve top-k memories under token budget. Graph edges help multi-hop personal knowledge; start with flat facts if learning-focused.

### [12] Memory evals: LOCOMO multi-session benchmark + DMR/LongMemEval; memory systems beat RAG/full-context on latency/cost and multi-hop/temporal QA
- quote: "evaluations on LOCOMO benchmark... against... (ii) retrieval-augmented generation (RAG) with varying chunk sizes and k-values, (iii) a full-context approach... consistently outperform all existing memory systems across four question categories: single-hop, temporal, multi-hop, and open-domain." Zep: "Deep Memory Retrieval (DMR)... 94.8% vs 93.4% [MemGPT]... LongMemEval... accuracy improvements of up to 18.5% while simultaneously reducing response latency by 90%"
- url: https://arxiv.org/abs/2504.19413 ; https://arxiv.org/abs/2501.13956
- source_type: papers
- published: 2025-04 / 2025-01
- confidence: medium-high
- implementation: Eval plan for 俱佳Agent memory: (1) factual recall after session restart; (2) temporal questions ("what did I say last week"); (3) multi-hop preference+task consistency; (4) token cost / p95 latency vs full-history baseline. Prefer LLM-as-judge + golden traces. Use LOCOMO-style categories even if not shipping the full dataset.

### [13] Long-horizon context strategies: compaction vs note-taking vs sub-agent handoff
- quote: "Compaction maintains conversational flow for tasks requiring extensive back-and-forth; Note-taking excels for iterative development with clear milestones; Multi-agent architectures handle complex research... Each subagent... returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)."
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: official vendor engineering guide
- published: 2025-09-29
- confidence: high
- implementation: Conversation handoff packet should be ≤~2k tokens: objective, constraints, completed steps, key IDs, open questions. Sub-agents isolate noisy search/tool context; parent keeps only distilled results. Use all three depending on task class.

### [14] Simple composable agent patterns + clear tool interfaces matter more than heavy memory frameworks
- quote: "the most successful implementations use simple, composable patterns rather than complex frameworks... basic building block... is an LLM enhanced with augmentations such as retrieval, tools, and memory... Maintain simplicity... Prioritize transparency... Carefully craft your agent-computer interface"
- url: https://www.anthropic.com/engineering/building-effective-agents
- source_type: official vendor engineering guide
- published: 2024-12-19
- confidence: high
- implementation: Do not start by embedding Mem0/Letta as a hard dependency. Start with: pinned memory blocks + session log + note tools + compaction; add vector index when archival search is a real need. Tool schemas for memory ops must be as carefully designed as any other tool.

### [15] Implementation blueprint for TypeScript+Electron personal learning agent (synthesis from above sources)
- quote: N/A — synthesis of findings [1][3][4][6][7][8][11][14] into engineering guidance (not a single external claim)
- url: see source URLs above
- source_type: engineering synthesis for 俱佳Agent
- published: 2026-09-18
- confidence: medium
- implementation: Suggested local layout: `userData/memory/` → `core.json` (semantic blocks, schema versioned), `sessions/<sessionId>.jsonl` (append-only episodic), `notes/` (agentic markdown), optional `vectors.sqlite` (chroma/sqlite-vec). Atomic write: temp file → rename; never partial-write core.json. Context assembler: budget tokens for [system+core | tools | retrieved_memories k≤N | sliding_window | reserved]. Compaction threshold + handoff summary written back into session memory. Retrieval: hybrid (BM25/file search + embeddings) with k and max_tokens caps. Eval harness: restart-recall + temporal + multi-hop probes.
