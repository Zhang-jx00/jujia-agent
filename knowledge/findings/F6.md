# F6: Performance, preload, cache and fluid UI for desktop agents

## Findings

### [1] Electron's official performance checklist starts with measurement: profile first, then optimize the hottest path; multi-process work needs Chrome Tracing, not only single-process DevTools.
- quote: "The most successful strategy for building a performant Electron app is to profile the running code, find the most resource-hungry piece of it, and to optimize it... For advanced analysis looking at multiple processes at once, consider the Chrome Tracing tool."
- url: https://www.electronjs.org/docs/latest/tutorial/performance
- source_type: primary
- published: unknown (current Electron docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Electron maintainers' performance doctrine, citing VS Code "The First Second" and Chrome DevTools Performance analysis.
- **Why it matters for a desktop agent**: 俱佳Agent has main + renderer + utility/sidecar processes; renderer-only profiling misses IPC and main-process stalls that freeze the whole app.
- **Implementation takeaway**: Instrument cold-start (window ready → first interactive chat shell), stream-time FPS, and heap growth. Use DevTools Performance for the renderer and `about:tracing` / Chrome Tracing for cross-process IPC jank. Prefer `node --cpu-prof --heap-prof -e "require('module')"` when auditing heavy deps (e.g. model SDK clients).

### [2] About:tracing records hierarchical C++/JS events per thread per process and is the tool for framerate variation and multi-process bottlenecks in Electron.
- quote: "Tracing records activity in Chrome's processes... It records C++ or javascript method signatures in a hierarchical view for each thread in each process... events with irregular lengths (leading to e.g. framerate variation)."
- url: https://www.chromium.org/developers/how-tos/trace-event-profiling-tool/
- source_type: primary
- published: unknown (current Chromium how-to, accessed 2026-09-18)
- confidence: high
- **What it is**: Chromium multi-process trace tooling (`about:tracing`), recommended by Electron for multi-process analysis.
- **Why it matters for a desktop agent**: Streaming token IPC + markdown re-parse + layout can create jank that only appears when main, renderer, and GPU interact.
- **Implementation takeaway**: Capture traces while a long agent run streams tool logs; look for main-process UI-thread long tasks, renderer scripting vs style/layout, and frame drops. Pair with Frame Viewer docs for jank case studies.

### [3] Load and run code too soon is a top Electron pitfall: allocate resources just-in-time, defer heavy `require()` until first use (especially costly on Windows).
- quote: "If you have expensive setup operations, consider deferring those... Loading modules is a surprisingly expensive operation, especially on Windows... allocate resources 'just in time' rather than allocating them all when your app starts."
- url: https://www.electronjs.org/docs/latest/tutorial/performance
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Deferred loading pattern; VS Code paints unhighlighted text first, then highlights.
- **Why it matters for a desktop agent**: Model catalog parsers, markdown/mermaid/highlight.js, and tool SDKs are not needed for first paint of the chat shell.
- **Implementation takeaway**: Route-level React.lazy for settings/model panels; dynamic `import()` for syntax highlighters and diff engines; defer model-catalog parse until the model picker opens. Show conversation chrome first, analytics/update checks after `requestIdleCallback`.

### [4] Carelessly included modules and multi-file `require()` graphs destroy startup; bundle main and preload, audit dependency cost before adding packages.
- quote: "When considering a module, we recommend that you check: 1. the size of dependencies included 2. the resources required to load (`require()`) it... we heavily recommend that you bundle all your code into one single file to ensure that the overhead included in calling `require()` is only paid once."
- url: https://www.electronjs.org/docs/latest/tutorial/performance
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Module-cost discipline + bundling recommendation (electron-builder/forge + vite/esbuild/webpack dual environment).
- **Why it matters for a desktop agent**: A single "popular" npm package can pull 100k-line JSON parses at require-time; Windows desktop users feel this as multi-second cold start.
- **Implementation takeaway**: Bundle main and preload to single files; use `node --cpu-prof --heap-prof` before adopting SDKs; strip polyfills (Electron ships modern Chromium); target current ES in TypeScript config; call `Menu.setApplicationMenu(null)` before `app.on('ready')` when using a frameless/custom menu.

### [5] Never block the main process: avoid sync IPC, `@electron/remote`, and sync `fs`; offload CPU work to worker threads / renderer / UtilityProcess.
- quote: "Under no circumstances should you block this process and the UI thread with long-running operations... For long running CPU-heavy tasks, make use of worker threads... Avoid using the synchronous IPC and the `@electron/remote` module... prefer the asynchronous and non-blocking variant."
- url: https://www.electronjs.org/docs/latest/tutorial/performance
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Main-process responsiveness rules; main is the control tower for OS events and GPU coordination.
- **Why it matters for a desktop agent**: Agent runs do heavy disk I/O (workspace scans, git, logs) and streaming IPC; main-thread freezes freeze every window.
- **Implementation takeaway**: Prefer `ipcRenderer.invoke` + `ipcMain.handle` over `sendSync`; use async `fs.promises`; host long-running agent/sidecar work in `UtilityProcess` or Node worker_threads; keep main as a thin router.

### [6] Avoid `ipcRenderer.sendSync`: it blocks the renderer until main replies; IPC uses Structured Clone so DOM/Node-native Electron objects cannot cross the boundary.
- quote: "we recommend **avoiding this API** for performance reasons. Its synchronous nature means that it'll block the renderer process until a reply is received... Electron's IPC implementation uses the HTML standard Structured Clone Algorithm to serialize objects... DOM objects... Node.js objects backed by C++ classes... Electron objects backed by C++ classes... are not serializable."
- url: https://www.electronjs.org/docs/latest/tutorial/ipc
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Official IPC performance and serialization constraints; preload must expose narrow APIs via `contextBridge`, not raw `ipcRenderer`.
- **Why it matters for a desktop agent**: Streaming tool events must be async; large transcripts must not be re-cloned wholesale every token.
- **Implementation takeaway**: Design token/chunk events as small structured payloads `{sessionId, messageId, delta, seq}`; never ship full message history per token; expose `onAgentEvent(cb)`/`offAgentEvent()` in preload with unsubscribe to avoid listener leaks; do not pass file handles or Electron objects through IPC.

### [7] Preload scripts run in the renderer before web content with Node privileges but contextIsolation keeps them out of page `window` unless exposed via `contextBridge`—keep preload thin and API-shaped, not a mini-app.
- quote: "Preload scripts contain code that executes in a renderer process before its web content begins loading... you cannot directly attach any variables from the preload script to `window` because of the `contextIsolation` default... use the `contextBridge` module to accomplish this securely."
- url: https://www.electronjs.org/docs/latest/tutorial/process-model
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Process-model definition of preload + context isolation; utility process available for crash-prone/CPU work with MessagePort to renderer.
- **Why it matters for a desktop agent**: Preload is on the cold-start path; heavy preload delays FCP-equivalent (first interactive chat UI) even when the renderer bundle is ready.
- **Implementation takeaway**: Preload = IPC façade only (start/stop run, cancel, event subscribe, config get/set, dialog). Do not load model catalogs, parsers, or logging frameworks in preload. Prefer MessagePort/utility process for high-volume agent streams so main is not a bottleneck broker.

### [8] react-window virtualizes large lists by rendering only the visible window; List supports fixed, percentage, function, or `useDynamicRowHeight` heights, with `overscanCount` to reduce edge flicker.
- quote: "`react-window` is a component library that helps render large lists of data quickly and without the performance problems that often go along with rendering a lot of data... Dynamic row heights are not as efficient as predetermined sizes. It's recommended to provide your own height values if they can be determined ahead of time... overscanCount: How many additional rows to render outside of the visible area."
- url: https://github.com/bvaughn/react-window
- source_type: primary
- published: unknown (current main README, accessed 2026-09-18; library used in React DevTools)
- confidence: high
- **What it is**: Industry-standard React windowing for long chat/tool transcripts (17k+ stars; same author as react-virtualized, lighter API).
- **Why it matters for a desktop agent**: Multi-hour coding sessions produce thousands of message/tool blocks; full DOM render kills scroll and memory.
- **Implementation takeaway**: Virtualize the conversation list; pin the actively streaming bubble outside the virtualizer or force-scroll via imperative `listRef`. Prefer estimated stable heights per message kind (user/assistant/tool/error) and measure only the streaming tail. Use `rowKey` + `useCallback` for stable identity; `onRowsRendered` to lazy-load older history.

### [9] `requestIdleCallback` queues low-priority main-thread work for idle periods so animation and input stay responsive; always set `timeout` for work that must run.
- quote: "The `window.requestIdleCallback()` method queues a function to be called during a browser's idle periods. This enables developers to perform background and low priority work on the main thread, without impacting latency-critical events such as animation and input response... A `timeout` option is strongly recommended for required work."
- url: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback
- source_type: primary
- published: modified 2025-06-23 (MDN)
- confidence: high
- **What it is**: Cooperative scheduling API recommended by Electron docs for renderer non-urgent work.
- **Why it matters for a desktop agent**: Token paint is latency-critical; telemetry, transcript autosave, embedding-index updates are not.
- **Implementation takeaway**: Schedule autosave/index/telemetry via `requestIdleCallback` with explicit `timeout`; check `IdleDeadline.timeRemaining()` and chunk work; cancel idle callbacks on session switch to avoid cross-session writes.

### [10] Web Workers run JS off the UI thread; Electron can enable Node in workers via `nodeIntegrationInWorker`, but native modules in workers are unsafe because `process.dlopen` is not thread-safe.
- quote: "Web Workers are a simple means for web content to run scripts in background threads. The worker thread can perform tasks without interfering with the user interface... data is sent between workers and the main thread via a system of messages... The only way to load a native module safely for now, is to make sure the app loads no native modules after the Web Workers get started."
- url: https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers ; https://www.electronjs.org/docs/latest/tutorial/multithreading
- source_type: primary
- published: MDN modified 2026-08-27; Electron multithreading current docs
- confidence: high
- **What it is**: OS-thread offloading for renderer CPU work; Electron multi-threading caveats (`sandbox` must not be true; SharedWorker/ServiceWorker lack nodeIntegrationInWorker).
- **Why it matters for a desktop agent**: Markdown AST builds, diff algorithms, JSON schema validation of tool results, and local search can block streaming paint if run on the UI thread.
- **Implementation takeaway**: Offload pure computation to workers; use `postMessage` + Transferables (`ArrayBuffer`) for large blobs to avoid structured-clone copies; optionally SharedArrayBuffer for hot shared buffers; pattern for Electron: `process.dlopen = () => { throw new Error('Load native module is not safe') }` before spawning workers if any native modules exist. Prefer UtilityProcess over worker+native for native-dependent tooling.

### [11] Event batching / debounce / throttle vs React deferred rendering: for streaming chat UI, prefer interruptible deferred updates (`useDeferredValue`) over fixed-delay debounce when work happens during render; still debounce non-render side effects.
- quote: "Debouncing means you'd wait for the user to stop typing... Throttling means you'd update the list every once in a while... `useDeferredValue` is better suited to optimizing rendering because it is deeply integrated with React itself and adapts to the user's device... deferred re-renders... are interruptible by default... debouncing and throttling still produce a janky experience because they're *blocking*."
- url: https://react.dev/reference/react/useDeferredValue
- source_type: primary
- published: unknown (current React reference, accessed 2026-09-18)
- confidence: high
- **What it is**: Official React guidance contrasting debounce/throttle with deferred values; `memo` required on slow lists so deferred props can skip re-render.
- **Why it matters for a desktop agent**: LLM tokens arrive at high frequency; naive setState-per-token re-renders the entire transcript.
- **Implementation takeaway**: Coalesce IPC deltas in a buffer and flush on `requestAnimationFrame` or a 32–50ms interval; keep the streaming message text in a ref/local buffer and commit to React state at frame cadence; use `useDeferredValue` for expensive derived views (diff panels, token stats) so typing/scroll stays snappy; wrap completed messages in `memo`/immutable snapshots so only the tail re-renders. Debounce search/config validation (100–300ms); throttle scroll-follow logic.

### [12] Local assets beat CDN for desktop: bundle fonts/icons/static model cards; measure with Network tab + Disable cache + throttling; Service Workers for updatable resources.
- quote: "Avoid fetching rarely changing resources from the internet if they could easily be bundled with your application... download the fonts and include them in your app's bundle... open up the developer tools. Navigate to the `Network` tab and check the `Disable cache` option... enable `Network Throttling`."
- url: https://www.electronjs.org/docs/latest/tutorial/performance
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Offline-first asset strategy for Electron; ideal app needs no network to boot UI.
- **Why it matters for a desktop agent**: Windows users may be offline; model catalog / logo / fonts should not gate first paint.
- **Implementation takeaway**: Ship design-system fonts and icons in the asar; cache model catalog and provider metadata on disk (JSON + mtime/etag); treat remote model lists as background refresh over a local snapshot. First contentful paint target for agent UI = shell + last session transcript stub + composer, not full remote config.

### [13] Layered cache for agent desktop: process-memory hot cache → disk snapshot (config, model catalog, sessions) → network refresh; invalidate on version/user change; never block first paint on remote fetch.
- quote: (derived) Electron guidance: do not load unused modules at startup; avoid unnecessary/blocking network requests; allocate just-in-time. React docs show Map-based request caches for deferred UI data.
- url: https://www.electronjs.org/docs/latest/tutorial/performance ; https://react.dev/reference/react/useDeferredValue
- source_type: primary-derived
- published: unknown (docs accessed 2026-09-18)
- confidence: medium
- **What it is**: Application of official Electron/React guidance to agent-specific cache layers (config, model catalog, assets, transcript indexes).
- **Why it matters for a desktop agent**: Model switching, provider credentials, and session restore must feel instant; cold network model lists create multi-second blank model pickers.
- **Implementation takeaway**: L1 in-memory immutable config object in main, broadcast via IPC on change; L2 disk (`userData/config.json`, `model-catalog.json`) written debounced (e.g. 300–500ms) and read synchronously only at boot after async file read on a worker if large; L3 network refresh with TTL + ETag, UI shows stale-while-revalidate. Asset cache: content-hash filenames in app bundle; optional `session.defaultSession` HTTP cache for remote model cards. Session transcripts: IndexedDB/local files, virtualized UI loads only visible pages.

### [14] Renderer memory-leak patterns in Electron agent UIs: uncleaned `ipcRenderer.on` listeners, retained full transcripts in React state, detached DOM from non-virtualized lists, and uncleared intervals/workers across session switches.
- quote: "don't just pass the callback to `ipcRenderer.on` as this will leak `ipcRenderer` via `event.sender`. Use a custom handler that invokes the `callback` only with the desired arguments."
- url: https://www.electronjs.org/docs/latest/tutorial/ipc
- source_type: primary
- published: unknown (current IPC docs security note; leak classes derived for agent UIs)
- confidence: medium
- **What it is**: Official warning on IPC listener exposure plus standard Chromium renderer leak classes when long agent sessions accumulate DOM/state.
- **Why it matters for a desktop agent**: Desktop agents stay open for hours; leaks show as progressive scroll jank and eventual OOM on Windows.
- **Implementation takeaway**: Preload returns unsubscribe functions; React `useEffect` cleanup removes all IPC subscriptions and aborts streams on unmount; cap in-memory message windows (keep last N fully hydrated, hydrate older from disk on scroll); virtualize lists (finding 8); terminate workers on session change; use DevTools Memory heap snapshots before/after 10 conversation switches; watch detached `HTMLDivElement` counts. Avoid storing full tool stdout in React state—store pointers + streaming tail.

### [15] First-paint / fluidity targets for agent chat: paint interactive shell before agent bootstrap; keep main-thread scripting per frame under ~8–16ms during streams; coalesce layout reads/writes to avoid thrash.
- quote: (derived) Electron: "execute operations as quickly as possible without taking away resources needed to keep scrolling smooth, respond to user input, or animations at 60fps... users complain about your app sometimes 'stuttering'." Chromium tracing docs emphasize diagnosing framerate variation via per-thread events.
- url: https://www.electronjs.org/docs/latest/tutorial/performance ; https://www.chromium.org/developers/how-tos/trace-event-profiling-tool/
- source_type: primary-derived
- published: unknown (docs accessed 2026-09-18)
- confidence: medium
- **What it is**: Applied performance budgets for a streaming desktop agent UI; layout thrash = interleaved DOM reads (getBoundingClientRect) and writes during stream commits.
- **Why it matters for a desktop agent**: Users judge "fluidity" by scroll + typing during generation, not by offline benchmarks.
- **Implementation takeaway**: Budget: shell interactive < 1–2s cold start on mid Windows laptop; stream frame budget leave headroom for input; measure FCP-like via `performance.mark` around first composer focusable + last-session title paint. Batch scroll follow: read scroll position once per rAF, write `scrollTop` once; avoid measuring every message height every token. Prefer CSS transforms/opacity for UI chrome animations; keep markdown incremental (append to last text node / last block) rather than full re-parse of entire message each flush. Use `content-visibility` carefully; validate with Performance panel long tasks and Chrome Tracing frame viewer.

### [16] IPC + streaming architecture for fluid agent UI: main/utility produces deltas, renderer coalesces; main-to-renderer uses `webContents.send` / MessagePort; do not round-trip every token through heavy handlers.
- quote: "When sending a message from the main process to a renderer process, you need to specify which renderer is receiving the message... via its `WebContents` instance... Pass a MessagePort from the main process to both renderers. This will allow direct communication between renderers after the initial setup."
- url: https://www.electronjs.org/docs/latest/tutorial/ipc ; https://www.electronjs.org/docs/latest/tutorial/process-model
- source_type: primary
- published: unknown (current docs, accessed 2026-09-18)
- confidence: high
- **What it is**: Official main→renderer and MessagePort patterns for high-volume agent streams.
- **Why it matters for a desktop agent**: Token/tool-event throughput determines perceived quality; blocked main or unbatched IPC equals stutter.
- **Implementation takeaway**: Run model client + tool executor in UtilityProcess/worker; stream deltas to renderer via MessagePort when volume is high; batch protocol: producer coalesces to ≥16–50ms windows or N bytes; renderer applies frame-synced commits; backpressure by pausing tool-log DOM hydration when virtual list scroll is not at bottom (only update badge). Persist transcript asynchronously on idle (finding 9).
