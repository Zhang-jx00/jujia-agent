# F5: System architecture and Electron engineering

## Findings

### [1] Electron multi-process model: one main + one renderer per window
**Claim**: Electron inherits Chromium's multi-process architecture. The app has a **single main process** (Node.js entry point, window/lifecycle/native APIs) and **one renderer process per `BrowserWindow`/web embed**. Destroying a `BrowserWindow` terminates its renderer.
**Quote**: "Each Electron app has a single main process, which acts as the application's entry point. The main process runs in a Node.js environment… Each Electron app spawns a separate renderer process for each open BrowserWindow… When a BrowserWindow instance is destroyed, its corresponding renderer process gets terminated as well."
**URL**: https://www.electronjs.org/docs/latest/tutorial/process-model
**Source type**: Electron official docs
**Published**: docs/latest (fetched 2026-09-18; Electron 44.4.2 referenced in security page)
**Confidence**: high

**Implementation takeaway (俱佳Agent)**: Put agent orchestration, tool execution, file/system access, and window ownership in **main** (or a utility/sidecar). Renderer = pure UI. Never treat a renderer as the agent brain — a pet window crash must not kill the agent session.

---

### [2] Preload scripts are the only sanctioned bridge into renderers
**Claim**: Preload runs in the renderer **before** page load, can `require` limited Node/Electron modules, and is attached via `webPreferences.preload`. With contextIsolation on, you **cannot** assign onto `window` directly; use `contextBridge.exposeInMainWorld`.
**Quote**: "Preload scripts contain code that executes in a renderer process before its web content begins loading… you cannot directly attach any variables from the preload script to window because of the contextIsolation default… Instead, use the contextBridge module… contextBridge.exposeInMainWorld('myAPI', { desktop: true })"
**URL**: https://www.electronjs.org/docs/latest/tutorial/process-model
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Design a **narrow typed bridge API** (`window.agent.*`) in preload — e.g. `runTool`, `listSessions`, `onAgentEvent`, `terminal.write` — not a raw IPC surface. Type the Window interface in a `.d.ts` for TypeScript.

---

### [3] contextIsolation: separate JS worlds; default since Electron 12
**Claim**: Preload and Electron internals run in a **different** `window` object than page scripts. Isolation prevents renderer XSS from reaching privileged APIs/prototypes.
**Quote**: "the window object that your preload script has access to is actually a different object than the website would have access to… Context isolation has been enabled by default since Electron 12, and it is a recommended security setting for all applications."
**URL**: https://www.electronjs.org/docs/latest/tutorial/context-isolation
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Keep `contextIsolation: true` everywhere, including pet and browser-helper windows. Any legacy `window.X = api` pattern must migrate to `contextBridge`.

---

### [4] Never expose raw `ipcRenderer` over the bridge
**Claim**: `contextBridge` alone is not safe if you pass through powerful APIs without filtering. Expose **one method per IPC channel**, not `ipcRenderer.send`.
**Quote**: "this code is unsafe… contextBridge.exposeInMainWorld('myAPI', { send: ipcRenderer.send })… It directly exposes a powerful API without any kind of argument filtering… The correct way to expose IPC-based APIs would instead be to provide one method per IPC message."
**URL**: https://www.electronjs.org/docs/latest/tutorial/context-isolation
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Preload whitelist = security boundary. Agent IPC channels should be namespaced (`agent:ask`, `term:data`, `pet:state`) and mirrored 1:1 on the bridge object.

---

### [5] IPC patterns: send/on vs invoke/handle
**Claim**: Official IPC guide defines two primary renderer→main patterns: **one-way** `ipcRenderer.send` + `ipcMain.on`, and **two-way request/response** `ipcRenderer.invoke` + `ipcMain.handle` (Promise result). Channels are developer-defined and bidirectional by name. Errors from `handle` are not fully transparent (only `message` serializes).
**Quote**: "Inter-process communication (IPC) is a key part of building feature-rich desktop applications in Electron… Pattern 1: Renderer to main (one-way)… ipcRenderer.send… Pattern 2: Renderer to main (two-way)… ipcRenderer.invoke paired with ipcMain.handle… Errors thrown through handle in the main process are not transparent as they are serialized and only the message property from the original error is provided to the renderer process."
**URL**: https://www.electronjs.org/docs/latest/tutorial/ipc
**Source type**: Electron official docs
**Published**: docs/latest (Electron 44.4.2 fiddles)
**Confidence**: high

**Implementation takeaway**: Use **invoke/handle** for commands that need results (file pick, run tool, query session). Use **send + webContents events** for streaming agent tokens/tool events to UI. Define a typed IPC contract package shared by main and renderer. Structured error objects (`{code, message}`) because default Error serialization is lossy.

### [6] Sandbox on by default since Electron 20; sandboxed preload has a tiny require surface
**Claim**: Chromium sandbox limits renderer to CPU/memory; privileged work must go via IPC to main. Sandboxed preloads get a **polyfilled subset** of Node requires: `electron` renderer modules (`contextBridge`, `ipcRenderer`, …), `events`, `timers`, `url`. You cannot split preload via CommonJS `require` without a bundler. Enabling `nodeIntegration` disables sandbox. `app.enableSandbox()` forces it app-wide before ready.
**Quote**: "Starting from Electron 20, the sandbox is enabled for renderer processes without any further configuration… when the sandbox is enabled, renderer processes can only perform privileged tasks… by delegating these tasks to the main process via inter-process communication (IPC)… preload scripts attached to sandboxed renderers will still have a polyfilled subset of Node.js APIs… Because the require function is a polyfill… you will not be able to use CommonJS modules to separate your preload script into multiple files. If you need to split your preload code, use a bundler…"
**URL**: https://www.electronjs.org/docs/latest/tutorial/sandbox
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Keep sandbox **on**. Bundle preload (esbuild/webpack/vite plugin). Do **not** put agent runtime in renderer to "use native modules" — that forces `sandbox:false`/`nodeIntegration` and is a security regression. Native/heavy work → main, utility process, or sidecar.

### [7] Official 20-item Electron security checklist
**Claim**: Electron publishes a checklist including: only load secure content; no Node for remote content; enable contextIsolation; enable sandbox; `ses.setPermissionRequestHandler`; do not disable `webSecurity`; CSP (`script-src 'self'`); no `allowRunningInsecureContent`; no experimental Blink features; careful `<webview>` options; limit navigation/new windows; validate `shell.openExternal`; current Electron version; **validate IPC sender**; prefer custom protocols over `file://`; check fuses; do not expose Electron APIs to untrusted content.
**Quote**: "You should at least follow these steps to improve the security of your application: 1. Only load secure content… 3. Enable context isolation in all renderers 4. Enable process sandboxing… 7. Define a Content-Security-Policy… 17. Validate the sender of all IPC messages 18. Avoid usage of the file:// protocol and prefer usage of custom protocols… 20. Do not expose Electron APIs to untrusted web content"
**Also**: "Under no circumstances should you load and execute remote code with Node.js integration enabled… to display remote content, use the `<webview>` tag or a WebContentsView and make sure to disable the nodeIntegration and enable contextIsolation."
**URL**: https://www.electronjs.org/docs/latest/tutorial/security
**Source type**: Electron official docs
**Published**: docs/latest (SECURITY.md ref Electron v44.4.2)
**Confidence**: high

**Implementation takeaway for 俱佳Agent (browser/pet windows)**: Agent shell UI = local + trusted. In-app **browser** window that loads arbitrary URLs = separate `BrowserWindow`/`WebContentsView` with **no** preload bridge to agent APIs, `contextIsolation:true`, sandbox on, navigation allowlist, `setWindowOpenHandler` deny, CSP on agent UI, IPC `event.senderFrame` validation on every handle.

### [8] UtilityProcess: preferred Node child/sidecar over raw child_process.fork
**Claim**: `utilityProcess.fork(modulePath, args, options)` creates a Chromium Services child with Node + MessagePorts. Prefer it over `child_process.fork` when forking from main. Options include `stdio` (pipe/inherit/ignore stdout/stderr), `serviceName` (appears in metrics / `child-process-gone`), `session`/`partition`, macOS `disclaim` for untrusted code. Fork only after `app` ready.
**Quote**: "utilityProcess creates a child process with Node.js and Message ports enabled. It provides the equivalent of child_process.fork API from Node.js but instead uses Services API from Chromium… An Electron app can always prefer the UtilityProcess API over Node.js child_process.fork API when there is need to fork a child process from the main process… serviceName… will appear in… child-process-gone event of app… utilityProcess.fork can only be called after the ready event has been emitted on App."
**URL**: https://www.electronjs.org/docs/latest/api/utility-process
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Host the **agent runtime / tool runner / LLM session loop** in a `utilityProcess` (or external sidecar if it needs its own lifecycle beyond Electron). Main stays a thin window+IPC router. `serviceName: 'agent-runtime'` enables crash attribution via `app.on('child-process-gone')` for recovery UX.

### [9] Process-model guidance: utility process for untrusted / crash-prone / CPU-heavy work
**Claim**: Official process model says utility processes should host "untrusted services, CPU intensive tasks or crash prone components" that would otherwise live in main; difference vs `child_process.fork` is MessagePort channels to renderers.
**Quote**: "The utility process can be used to host for example: untrusted services, CPU intensive tasks or crash prone components which would have previously been hosted in the main process… the primary difference between the utility process and process spawned by Node.js child_process module is that the utility process can establish a communication channel with a renderer process using MessagePorts."
**URL**: https://www.electronjs.org/docs/latest/tutorial/process-model
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Map agent subsystems: **UI renderer** ↔ **main (windows, tray, update, IPC hub)** ↔ **agent utility process (sessions, tools)** ↔ optional **OS binaries** (user shells). Crash-prone tool code must not sit in main.

### [10] TypeScript process-boundary module aliases
**Claim**: Electron npm package exports type subpaths `electron/main`, `electron/renderer`, `electron/common` for process-scoped typing; no runtime effect.
**Quote**: "electron/main includes types for all main process modules. electron/renderer includes types for all renderer process modules. electron/common includes types for modules that can run in main and renderer process… These aliases have no impact on runtime, but can be used for typechecking and autocomplete."
**URL**: https://www.electronjs.org/docs/latest/tutorial/process-model
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Enforce module boundaries in TS: `src/main/**` imports `electron/main`, `src/preload/**` and UI import only bridge types from `src/shared/ipc-contracts`. Lint rule: renderer packages must not import main-only modules.

### [11] node-pty terminals: xterm.js in renderer + node-pty in main + IPC
**Claim**: Microsoft's official Electron example wires **xterm.js on the renderer** and **node-pty on the main process**, communicating via IPC.
**Quote**: "This is a minimal example of getting a terminal running in Electron using node-pty and xterm.js. It works by using xterm.js on the renderer process and node-pty on the main process with IPC to communicate back and forth."
**URL**: https://github.com/microsoft/node-pty/blob/main/examples/electron/README.md
**Source type**: Official GitHub example (microsoft/node-pty)
**Published**: repo main branch (fetched 2026-09-18)
**Confidence**: high

**Implementation takeaway**: Embedded agent shell for 俱佳Agent: PTY host in **main or a dedicated utility** (node-pty is a native module — rebuild for Electron ABI). Renderer streams bytes via bridge (`term:create/data/resize/kill`). Multiple sessions = map `ptyId → PTY`. Do not require node-pty in renderer (breaks sandbox). Package `node-pty` as an external/native dependency for electron-builder unpack.

### [15] Security posture for agent apps displaying untrusted content
**Claim**: Electron is not a browser; JS in the app can access filesystem/shell. Popular Electron apps primarily show local or trusted remote content **without Node integration**. Remote content must use WebContentsView/webview with `nodeIntegration` disabled and `contextIsolation` enabled. App security = framework + dependencies + your code; keep Electron current.
**Quote**: "Electron is not a web browser… JavaScript can access the filesystem, user shell, and more… the most popular Electron apps (Atom, Slack, Visual Studio Code, etc) display primarily local content (or trusted, secure remote content without Node integration)… Keep your application up-to-date with the latest Electron framework release… Evaluate your dependencies… Adopt secure coding practices."
**URL**: https://www.electronjs.org/docs/latest/tutorial/security
**Source type**: Electron official docs
**Published**: docs/latest
**Confidence**: high

**Implementation takeaway**: Security checklist for 俱佳Agent release:
1. `contextIsolation: true`, sandbox on, `nodeIntegration: false` on all windows
2. Preload bridge method-whitelist only
3. CSP `script-src 'self'` on agent UI
4. IPC sender validation + channel allowlist
5. Untrusted browser window: **zero** agent preload; partition isolation
6. Pin + upgrade Electron regularly
7. electron-builder code signing + fuse review
8. Do not `shell.openExternal` on model-generated URLs without scheme allowlist (`https:` only)
9. Tool side effects (shell, file write) gated in privileged process with user policy, not renderer
10. Prefer custom protocol (`app://`) over `file://` if loading packaged UI

### [16] Large-app structure pattern from agent codebases
**Source type**: GitHub repo listings
**Published**: live (fetched 2026-09-18)
**Confidence**: medium-high (folder layout is strong; deep package roles not fully expanded in fetched HTML)

**Implementation takeaway — proposed 俱佳Agent monorepo**:
```
packages/
  shared/          # IPC contracts, zod schemas, event types
  agent-core/      # sessions, tools, providers, modes (Plan/Act)
  agent-host/      # utilityProcess entry: run sessions, spawn PTY
  ui/              # renderer React/Vue app (chat, tools, files)
apps/
  desktop/         # Electron main, preload, electron-builder config
  pet/             # optional same-binary multi-window routes
sdks/              # future programmatic API
evals/             # harness + golden transcripts
```
Main process files stay small: `app-ready`, `windows`, `ipc-router`, `updater`, `pty-host`, `crash-guard`. Avoid one 2000-line `main.ts`.
