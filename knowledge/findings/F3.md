# F3: Skills, hooks, schedulers, connectors, MCP

## Findings

### [1] MCP is a JSON-RPC 2.0 host/client/server protocol that standardizes how LLM apps expose tools, resources, and prompts to external systems
- quote: "MCP provides a standardized way for applications to: Share contextual information with language models; Expose tools and capabilities to AI systems; Build composable integrations and workflows. The protocol uses JSON-RPC 2.0 messages to establish communication between: Hosts: LLM applications that initiate connections; Clients: Connectors within the host application; Servers: Services that provide context and capabilities."
- url: https://modelcontextprotocol.io/specification/2025-06-18
- source_type: primary
- published: 2025-06-18 (spec revision); current index also references 2026-07-28 schema
- confidence: high
- implementation_takeaway: 俱佳Agent should treat itself as MCP **Host**: Electron main process owns one **Client instance per MCP server**. Do not let a single client multiplex multiple servers; isolation is part of the security model. Prefer official TypeScript SDK (`@modelcontextprotocol/sdk` / `@modelcontextprotocol/client`) rather than hand-rolling JSON-RPC framing.

### [2] MCP servers offer Resources/Prompts/Tools; clients may offer Sampling/Roots/Elicitation; later protocol revision is more stateless and promotes Skills/MCP Apps via extensions
- quote: "Servers offer any of the following features to clients: Resources: Context and data, for the user or the AI model to use; Prompts: Templated messages and workflows for users; Tools: Functions for the AI model to execute. Clients may offer the following features to servers: Elicitation: Server-initiated requests for additional information from users. ... Notable extensions include: Tasks ... Skills over MCP ... MCP Apps."
- url: https://modelcontextprotocol.io/specification
- source_type: primary
- published: current index (schema 2026-07-28); 2025-06-18 revision still documented with Sampling + Roots
- confidence: high
- implementation_takeaway: Design the desktop agent tool surface around three primitives: **tools** (model-callable actions), **resources** (files/DB rows the model can read), **prompts** (user-invoked templates). Plan for Elicitation UI in Electron (dialogs that block tool execution) and optionally Tasks for long-running jobs. Track protocol revision carefully: 2025-06-18 is stateful; 2026-07-28 is described as stateless/self-contained with per-request capability negotiation.

### [3] MCP transports are stdio (client spawns server subprocess, newline-delimited JSON-RPC on stdin/stdout) and Streamable HTTP (POST/GET MCP endpoint, optional SSE, Mcp-Session-Id); HTTP+SSE from 2024-11-05 is deprecated
- quote: "The protocol currently defines two standard transport mechanisms for client-server communication: 1. stdio, communication over standard in and standard out 2. Streamable HTTP. Clients SHOULD support stdio whenever possible. ... In the stdio transport: The client launches the MCP server as a subprocess. The server reads JSON-RPC messages from its standard input (stdin) and sends messages to its standard output (stdout). Messages are delimited by newlines, and MUST NOT contain embedded newlines."
- url: https://modelcontextprotocol.io/specification/2025-06-18/basic/transports
- source_type: primary
- published: 2025-06-18
- confidence: high
- implementation_takeaway: For Windows Electron agents, default local connectors to **stdio** (npx/uvx spawn) and remote connectors to **Streamable HTTP**. On Windows, wrap npm launches as `cmd /c npx ...` (see official servers README). Streamable HTTP servers MUST validate `Origin` (DNS rebinding) and SHOULD bind localhost-only when local. Client must send `MCP-Protocol-Version` on subsequent HTTP requests and handle `Mcp-Session-Id` lifecycle + 404 → re-initialize.

### [4] MCP security model is host-enforced consent, not protocol-enforced: users must authorize data access and tool invocation; tool annotations are untrusted unless the server is trusted
- quote: "Users must explicitly consent to and understand all data access and operations ... Tool Safety: Tools represent arbitrary code execution and must be treated with appropriate caution. In particular, descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server. Hosts must obtain explicit user consent before invoking any tool."
- url: https://modelcontextprotocol.io/specification/2025-06-18
- source_type: primary
- published: 2025-06-18
- confidence: high
- implementation_takeaway: 俱佳Agent must implement **permission UI in the host** before `tools/call`. Never auto-approve remote MCP tools based on their own descriptions. Keep full conversation history in the host; do not forward entire transcript to every MCP server. Separate “approved connector registry” from “user-pasted server config.”

### [5] Official MCP security best practices call out confused-deputy OAuth proxies, token passthrough (forbidden), SSRF via OAuth discovery URLs, session hijacking, and local-server RCE
- quote: "Token passthrough is explicitly forbidden in the authorization specification ... MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server. ... If an MCP client supports one-click local MCP server configuration, it MUST implement proper consent mechanisms prior to executing commands. ... MCP clients MUST only allow http:// and https:// schemes for authorization URLs. ... MUST NOT use shell commands (e.g., cmd.exe, sh, PowerShell) to open URLs."
- url: https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices
- source_type: primary
- published: security best practices page (references auth spec 2025-11-25 + OAuth RFC9700)
- confidence: high
- implementation_takeaway: Critical for Electron Windows agent: (1) show exact stdio command before spawning any MCP server; (2) never open OAuth URLs via `cmd.exe`/PowerShell—use `shell.openExternal` only after scheme allowlist; (3) block private IP ranges when following OAuth metadata URLs if acting as a server-side/client hybrid; (4) sandbox local MCP servers; (5) use cryptographically random session IDs and never treat session IDs as auth.

### [6] Official MCP servers repo holds only a small set of reference implementations (Everything, Fetch, Filesystem, Git, Memory, Sequential Thinking, Time); production catalogs live in the MCP Registry; Windows stdio config uses `cmd /c npx`
- quote: "The servers in this repository are intended as reference implementations to demonstrate MCP features and SDK usage. They are meant to serve as educational examples ... not as production-ready solutions. ... If you are looking for a list of MCP servers, you can browse published servers on the MCP Registry (https://registry.modelcontextprotocol.io/). ... On Windows, wrap npx with cmd /c."
- url: https://github.com/modelcontextprotocol/servers
- source_type: primary
- published: repo state observed 2026-09-18 (~90.4k stars; GitHub/GitLab/Postgres/Brave etc. archived)
- confidence: high
- implementation_takeaway: Do not ship learning-agent features that depend on archived community servers without re-evaluating security. Prefer Registry for discovery. Ship a curated built-in set for 俱佳Agent (filesystem scoped to project dirs, memory graph, time, fetch) and treat everything else as user-installed third-party risk. Mirror the `mcpServers` JSON shape for connector settings so configs port from Claude Desktop / Cursor.

### [7] Agent Skills is an open folder format: required `SKILL.md` with YAML `name`/`description`, optional scripts/references/assets; progressive disclosure loads metadata → body → resources
- quote: "A skill is a directory containing, at minimum, a SKILL.md file ... name: Required. Max 64 characters. Lowercase letters, numbers, and hyphen only. ... description: Required. Max 1024 characters. ... Progressive disclosure: 1. Metadata (~100 tokens): The name and description fields are loaded at startup for all skills; 2. Instructions (< 5000 tokens recommended): The full SKILL.md body is loaded when the skill is activated; 3. Resources (as needed)."
- url: https://agentskills.io/specification
- source_type: primary
- published: open standard public since 2025-12-18 (Anthropic release note); site current as of research date
- confidence: high
- implementation_takeaway: Implement skill loading exactly as progressive disclosure: at agent boot inject only `name + description` into system prompt; on match, read `SKILL.md`; on demand read `references/*` and run `scripts/*`. Keep skill body under ~500 lines / <5k tokens. Validate name==dirname, lowercase hyphenated IDs. Windows path handling must accept both `/` and `\` in skill-relative references.

### [8] Anthropic introduced Agent Skills (2025-10-16) as folders of instructions/scripts/resources that agents discover dynamically; skills can complement MCP by teaching workflows that use external tools
- quote: "A skill is a directory containing a SKILL.md file that contains organized folders of instructions, scripts, and resources that give agents additional capabilities. ... Progressive disclosure is the core design principle that makes Agent Skills flexible and scalable. ... We'll also explore how Skills can complement Model Context Protocol (MCP) servers by teaching agents more complex workflows that involve external tools and software."
- url: https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills
- source_type: primary
- published: 2025-10-16 (updated note: open standard 2025-12-18)
- confidence: high
- implementation_takeaway: Architectural split for 俱佳Agent: **MCP = connectors/tools** (protocol, process boundary); **Skills = procedural knowledge** (markdown + optional code). Skills should document *how* to use MCP tools, not replace them. Security: install skills only from trusted sources; audit bundled scripts before execution—malicious skills are a prompt-injection + RCE vector.

### [9] Claude Code skills load from enterprise/personal/project/nested/plugin/claude.ai locations with frontmatter controlling invocation, tools, model, hooks, and subagent execution; custom commands merged into skills
- quote: "Create a skill when you keep pasting the same instructions... Unlike CLAUDE.md content, a skill's body loads only when it's used... Custom commands have been merged into skills. A file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy... Claude Code skills follow the Agent Skills open standard... Claude Code extends the standard with additional features like invocation control, subagent execution, and dynamic context injection."
- url: https://code.claude.com/docs/en/skills
- source_type: primary
- published: Claude Code docs, features versioned through v2.1.x (2026)
- confidence: high
- implementation_takeaway: For desktop agent skill management UI: support skill dirs at user-global + app-project scopes; frontmatter extensions worth porting: `disable-model-invocation`, `user-invocable`, `allowed-tools`/`disallowed-tools`, `model`/`effort` override, `context: fork` (subagent), `hooks` registered for the session. Live-reload SKILL.md on file change. Reserved-name collisions need a clear precedence table (enterprise > personal > project).

### [10] Claude Code hooks are deterministic lifecycle handlers (command/HTTP/prompt/agent) with event cadence: per-session, per-turn, and per-tool-call (PreToolUse/PostToolUse); they can block via permissionDecision JSON
- quote: "Hooks are user-defined shell commands, HTTP endpoints, MCP tool calls, LLM prompts, or subagents that execute automatically at specific points in Claude Code's lifecycle. ... Events fall into three cadences: per session: SessionStart and SessionEnd; per turn: UserPromptSubmit, Stop, and StopFailure; on every tool call inside the agentic loop: PreToolUse and PostToolUse. ... Exit code 0 with no output means the hook has no decision to report, so the tool call continues through the normal permission flow. The hook can deny the call, but staying silent doesn't approve it."
- url: https://code.claude.com/docs/en/hooks
- source_type: primary
- published: Claude Code hooks reference (v2.1.x era; async/prompt/agent hooks included)
- confidence: high
- implementation_takeaway: Implement a hook bus in Electron main with the same contract: fire PreToolUse before every tool execution; allow deny/allow/ask. Handlers: shell script on stdin JSON (Windows: PowerShell-friendly), optional HTTP webhook, optional LLM judge. Default-deny silent ≠ approve. Security: hooks run with user privileges—require workspace trust, review-before-run for project hooks, and Windows-specific quoting (`-NoProfile`, absolute paths).

### [11] Claude Code scheduling has three tiers: session-scoped `/loop` + CronCreate (1-min granularity, 7-day expiry, local timezone, deterministic jitter), Desktop local scheduled tasks (1-min min interval, needs app open + machine awake, catch-up once per missed slot), and cloud Routines (min 1 hour, no local files)
- quote: "Claude Code offers three ways to schedule recurring or one-off work: Cloud ... Desktop ... /loop ... Minimum interval: Cloud 1 hour; Desktop 1 minute; /loop 1 minute. ... Tasks are session-scoped: they live in the current conversation and stop when you start a new one. ... Desktop checks the schedule every minute while the app is open and starts a fresh session when a task is due ... Each task gets a small delay of a few minutes after the scheduled time to stagger API traffic."
- url: https://code.claude.com/docs/en/scheduled-tasks and https://code.claude.com/docs/en/desktop-scheduled-tasks
- source_type: primary
- published: docs current as of research (Desktop local tasks require Claude Desktop ≥ 1.1.5368)
- confidence: high
- implementation_takeaway: For 俱佳Agent Windows desktop: implement **local durable scheduled jobs** (not session-only): RRULE/cron expression, 1-minute floor, deterministic jitter, pause/resume, history, missed-run catch-up policy (exactly one), optional isolated worktree/folder, per-task permission mode. Store job definition on disk; do not rely on renderer session lifetime. Keep a separate future “cloud routine” path if learning agent must run when PC is off.

### [12] Claude Code Desktop stores local scheduled tasks as skill-like folders under `~/.claude/scheduled-tasks/<name>/SKILL.md` and exposes `update_scheduled_task` MCP tool for self-rescheduling
- quote: "To edit a task's prompt on disk, open ~/.claude/scheduled-tasks/<task-name>/SKILL.md ... The file uses YAML frontmatter for name and description, with the prompt as the body. ... A scheduled task can also modify its own schedule or prompt from within a running session using the update_scheduled_task MCP tool."
- url: https://code.claude.com/docs/en/desktop-scheduled-tasks
- source_type: primary
- published: Claude Code Desktop docs (local tasks post-1.1.5368)
- confidence: high
- implementation_takeaway: Convergence insight: **scheduled tasks are a skill packaging problem**. Represent every cron job as a skill package (SKILL.md + optional scripts) plus a schedule sidecar JSON (cron, folder, model, enabled, permissions). Allow the agent to edit its own schedule via a privileged internal tool—useful for learning loops (“re-run vocab review tomorrow”).

### [13] App connections / MCP installation in Claude Code use three scopes (local/project/user) + plugins + claude.ai connectors; project `.mcp.json` requires trust/approval; plugin MCP tools are namespaced `mcp__plugin_<plugin>_<server>__<tool>`
- quote: "MCP servers can be configured at several ways depending on your needs... Option 1: Add a remote HTTP server... Option 3: Add a local stdio server... MCP installation scopes: Local (current project only, ~/.claude.json); Project (shared via .mcp.json); User (all your projects, ~/.claude.json). ... For security reasons, Claude Code prompts for approval in interactive sessions before using project-scoped servers from .mcp.json files."
- url: https://code.claude.com/docs/en/mcp
- source_type: primary
- published: Claude Code MCP docs (v2.1.x; TypeScript SDK 1.x → 2.0 runtimes; protocol 2026-07-28 negotiation on v2)
- confidence: high
- implementation_takeaway: Connector UX for desktop agent: scopes = **App-global / Workspace / Session**; store secrets outside project VCS; always prompt on first connect for workspace-shared MCP configs; support `http`/`sse`/`stdio`/`ws` with `type` required when `url` present; namespace tools as `mcp__<server>__<tool>` for permission rules; discovery cache + lazy connect on first tool call improves startup on Windows.

### [14] Skills over MCP is an official MCP Working Group (charter 2026-04; SEP-2640 Skills Extension, Resources-based) coordinating distribution of agent skills through MCP + registry schema
- quote: "The Skills Over MCP Working Group defines how \"agent skills\" — rich, structured instructions for agent workflows — are discovered, distributed, and consumed through MCP. ... The WG's current direction is captured in SEP-2640 — Skills Extension (Resources-based, Extensions Track)."
- url: https://modelcontextprotocol.io/community/working-groups/skills-over-mcp
- source_type: primary
- published: charter changelog through 2026-04-25
- confidence: high
- implementation_takeaway: Do not invent a private skill-transfer protocol. Plan for skills to arrive over MCP Resources (`skill://` URI patterns are already used experimentally). Keep a skills store independent of transport so file-based and MCP-distributed skills share one registry. Watch registry `skills.json` proposal before shipping a public marketplace.

### [15] Microsoft Agent Framework (docs 2026-09-16) implements Agent Skills with 4-stage progressive disclosure tools (`load_skill`, `read_skill_resource`, `run_skill_script`) and experimental MCP-based skill discovery via `skill://index.json` (skill-md + archive types); archive scripts are never executed
- quote: "Agent Skills use a four-stage progressive disclosure pattern... 1. Advertise (~100 tokens per skill) ... 2. Load (< 5000 tokens recommended) - When a task matches a skill's domain, the agent calls the load_skill tool... 4. Run scripts... Skills can be discovered from MCP servers that expose skill resources under the skill:// URI scheme. ... Scripts bundled in archive-type skills are never executed. This is a deliberate security measure."
- url: https://learn.microsoft.com/en-us/agent-framework/agents/skills
- source_type: primary
- published: ms.date 2026-09-16
- confidence: high
- implementation_takeaway: Strong blueprint for 俱佳Agent skill runtime: expose internal tools `load_skill` / `read_skill_resource` / `run_skill_script` instead of stuffing skill bodies into the system prompt. Multiple skill sources (file, inline code, class-packaged, MCP) with aggregation/dedup/cache/filter pipeline. For remote/MCP skills: treat content as untrusted; refuse script execution from remote archives; require digest (`sha256:`) verification when present.

### [16] TypeScript MCP client embedding pattern: host constructs `Client` + `StdioClientTransport`, connects, `listTools()`, maps tools into model API schema, then loops `callTool` when the model emits tool_use
- quote: "import { Client } from \"@modelcontextprotocol/client\"; import { StdioClientTransport } from \"@modelcontextprotocol/client/stdio\"; ... this.transport = new StdioClientTransport({ command, args: [serverScriptPath] }); await this.mcp.connect(this.transport); const toolsResult = await this.mcp.listTools(); ... const result = await this.mcp.callTool({ name: toolName, arguments: toolArgs });"
- url: https://modelcontextprotocol.io/docs/2026-07-28/develop/build-client
- source_type: primary
- published: 2026-07-28 docs track (Node 20+; Windows path notes included)
- confidence: high
- implementation_takeaway: Electron blueprint: run MCP clients in **main process** (or a utility process), not in renderer; map `listTools` into provider tool schema at session start; handle `is_error` results as model-visible errors rather than crashes; on win32 choose correct spawn command (`python` vs `python3`, `cmd /c npx`); close transport on app quit; surface first-connect latency (~30s) in UI.

### [17] Skill “marketplaces” and packs are multi-layer: official standard at agentskills.io + Anthropic skills repo; Claude Code plugin marketplaces; claude.ai account sync (`~/.claude/skills/synced/`); third-party indexes (SkillsMP, AgenticSkills) catalog public GitHub skills
- quote: "Claude Code downloads a synced skill from your account rather than reading a file you wrote on the machine where the session runs... When the session starts, Claude Code downloads your account's skills into ~/.claude/skills/synced/ in the background, then checks claude.ai for changes about every 10 minutes... The Agent Skills format was originally developed by Anthropic, released as an open standard, and has been adopted by a growing number of agent products."
- url: https://code.claude.com/docs/en/skills ; https://agentskills.io/home
- source_type: primary (Claude Code + agentskills.io); marketplace indexes are secondary and not deeply audited here
- published: Claude Code docs current; agentskills.io client showcase includes Cursor, VS Code/GitHub Copilot, Gemini CLI, OpenCode, etc.
- confidence: medium
- implementation_takeaway: Marketplace strategy for learning agent: (1) ship built-in skill packs with the installer; (2) support installing skill folders from git URLs/local zip with trust review; (3) optional remote catalog later; (4) plugin bundle format can package skills + hooks + MCP servers together (`.claude-plugin/plugin.json` analog)—valuable for “course packs.” Treat third-party catalogs as untrusted discovery only.
