## 二、第 10 项为什么被提级：短名绕过敏感判定（实测）

报告原话只是"注释宣称 8.3 短名，代码里没实现"。读源码 + 上机实测之后，这件事的性质变了：

1. `packages/agent-core/src/tools/path-guard.ts:11` 的注释把"8.3 短名"列为**已逐条拒绝**的手法之一，
   但函数体里**没有任何对应分支**（其余五项设备路径 / UNC / ADS / 保留名 / 尾随点空格都在）；
2. 敏感判定 `packages/agent-core/src/permissions/policy.ts:78` 的 `SENSITIVE_PATH_PATTERNS` 是
   **纯词法正则**（`(^|[\\/])\.git([\\/]|$)` 这类）；
3. 本机 NTFS 实测（探针跑在 `.tmp`，用完即删）：
   `.git` → **`GIT~1`**、`.env` → **`ENV~1`**、`.npmrc` → **`NPMRC~1`**、`credentials` → **`CREDEN~1`**
   都确实能打开同一个对象；
4. 而 `realpathSync` **原样返回短名、不展开成长名** —— 所以注释第 3 条"检查真实路径"也挡不住它。

四条合起来：**把 `.git/config` 写成 `GIT~1/config` 就能让清单失配，从而"不问就读"敏感文件**。
这与已修的 T1（判定顺序洞）、T2（ADS 后缀洞）是同一个病：**换个写法让敏感清单认不出来**，
是本仓这条清单的第三条旁路。

**修法与为什么不修在守卫里**：短名**不破坏工作区边界**（`isInside` 与 realpath 对短名同样成立），
而在守卫里一律拒绝会把 `a~1.md` 这类合法文件名一起打死。真正需要补的是敏感判定那一侧，
于是判据落在 `packages/agent-core/src/permissions/short-name.ts`：
形状收得很紧（根名 1–8 字符 + `~` + 1–3 位序号 + 可选 1–3 字符扩展名，以点开头的长名一律不算），
`sensitiveReason` 在**清单没命中**时用它兜底成"这个名字我认不出来 → 按敏感对待、要人确认"
（fail closed，但不是 deny）—— 与同函数里"带流名就归到要问的一侧"是同一条推理。
守卫那边的注释改成实话，并写明"短名为什么不在这里管"。

**测试**：`permissions/short-name.test.ts` 7 例（含"9 字符根名 / 4 位序号 / 9 字符扩展名不误伤"三条边界）+
`policy.test.ts` 新增 1 例（短名读 `.git` 必须是**硬** ask：`expectHardAsk`）。
红→绿都跑过（先 `Cannot find module` + 断言红，实现后 79 例绿）。

## 三、第 1 项的普查结果（provider 层四条，按严重度）

原文没给内容，所以这里不是"核实"，是**对 `packages/agent-core/src/providers/` 的主动普查**。
四条都能指到代码位置，也都属于本仓最在意的类型：**静默**。

1. **带 `[DONE]` 的全垃圾流会被判成成功**（`openai-compat.ts:182–189` / `217–219`）：
   `mapPayload==='done'` 就 return，而"一个字都没收到 + 有解析失败的块 → `bad_response`"那条兜底
   只在**没有** `[DONE]` 的断流路径可达。后果：模型侧异常但流正常收尾时，界面显示一条**空回答**、
   账记成成功 —— 丢数据且没有说法。
2. **`finish_reason` 被归并成 `stop`**（`openai-compat.ts:308`，而 `types.ts:45` 的 `done` 只有 4 个变体）：
   `content_filer` / `length` 这类**截断**在界面上与"正常写完"一模一样。
3. **同一帧里的 usage 被吞**（`openai-compat.ts:318–320` 提前 return 了 `text_delta`，`:323` 的 usage 分支不可达）：
   末帧"正文 + usage"一起给的厂商，token 数丢在这里，整轮累计（`agent-loop.ts:213–216`）跟着少计 —— 统计**偏小**。
4. **没有 `index` 的 tool_calls 分片全并进 slot 0**（`tool-call-accumulator.ts:37`
   `const index = Number.isFinite(d.index) ? d.index : 0`）：
   省略 `index` 的兼容网关若同一帧给多个调用，name/arguments 会被串成一个 → 参数错乱或 parse 失败。

附带一条同族的：流终止后 `TextDecoder` 没有末次 `decode()` 冲刷（`openai-compat.ts:170`），
断流时尾部多字节字符静默丢。

这四条修复会碰到 `ProviderEvent` 联合（第 2 条要加变体）与既有 e2e 的假服务，
**整批改放在 R7**，不在本轮混做 —— 本轮的主调是核实与那条旁路。

## 四、第 8 项的两处差 1（为什么它不是"少显示一条"）

`chat-service.ts` 对同一个 sessionId 有两条取历史的路：**驻留内存**那条含 index 0 的 system 消息（`:200`/`:234`），
**从磁盘读**那条不含（`:272`，`:233` 注明"system 那条不落盘"）。于是 `total` 差 1：

- 盘上恰好 120 条时，hydrate 之后 `hasMore = 1`（`:275`），界面就给出"显示更早的 1 条"（`ChatPanel.tsx:806`），
  点开之后那 1 条是 system、被 `toBubbles` 过滤掉（`ChatPanel.tsx:266`）→ **按钮没反应，用户以为卡了**；
- 更狠的一条：resume 时记下 `loadedFrom`（`:298`），发第一条消息触发 hydrate、system 被前插（`ipc/chat.ts:126`），
  `loadOlder` 仍拿**旧口径**的 `before` 去查**新数组**（`ChatPanel.tsx:314–315`）→ 窗口整体少取一项，
  **有一条历史永远跳过、再也看不到**。

同一段代码里"数组含不含 system"这件事有两个答案，是典型的**两份判断重新分叉**（与 T15、R4 的
`decideStart` 同族）。修法应是把"历史窗口"的口径收敛到一个地方（含不含 system 由一处决定），
并把"取到 0 条可显示内容"这件事在界面上说出来而不是装成没按钮。→ **T33**，排 R6。
