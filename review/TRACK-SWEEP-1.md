## 〇、一句话结论

**代码主体是结实的，但"文档地基"已经塌了一角。** 具体说：
功能实现与安全承诺基本对得上（抽查 14 项全部一致），
**但状态与口径分散在 5 份文档里互相打脸**：同一批能力在 README 是"未开始"、在 PROGRESS 是"已完成"、
在 COVERAGE 是"待开发"；里程碑编号 M3/M4/M5 在不同文档指不同东西；
PLAN 里两条 ADR 级约束（utilityProcess、main ≤300 行）**从未兑现也未标注**。
更糟的是：**我上一轮建的 `check:docs` 恰好漏掉了这些漂移**（它不扫 PROGRESS 的数量、不扫 CHANGELOG 与 review/）。
这不是"楼歪了"，是**图纸与竣工图对不上，而且验收标准本身写错了**。

## 一、严重（必须先修）

### S1【已核实】权限模式切换是"假动作"：UI 提示成功，配置纹丝不动
- **证据**：`apps/desktop/src/main/ipc.ts:230-240` —— `CONFIG_SET` 用 `appConfigSchema.partial().parse()`
  收下整个 patch，然后**只挑 `theme` / `appearance` 写入**；`permissionMode` 通过校验后**被静默丢弃**，接口照常返回"成功"。
  渲染层 `PermissionRulesPanel.tsx:73-78` 调 `configSet({ permissionMode: next })` 后立即 `setMode(next)` 并提示"已切换为…"。
  而 `loadPolicy`（`ipc.ts:192-204`）读的是**落盘值**。
- **影响**：用户以为切到了 `plan`（只读）或 `acceptEdits`，实际仍在 `default`；刷新即回弹，**没有任何报错**。
  安全相关的静默失败 —— 与本项目"每个副作用动作都要你点头"的定位直接冲突。
- **同源问题**：`workspace`（我上轮刻意移出白名单）也是同样的静默丢弃；`alwaysAskTools` 同理。
  **白名单本身是合理的，错的是"丢弃不报错"。**

### S2【已核实】README「当前能力」把已交付的能力写成"未开始"
- **证据**：`README.md:134` `| **MCP Host** / 技能管理 / 定时任务 | ⏳ 未开始 |`
  而 W10a–e（MCP 四层 + 服务编排）、W11a–c（技能 + 插件清单 + 插件贡献 MCP）均已落地并写进 CHANGELOG。
- **影响**：对外唯一的能力声明让使用者**不会去配置 MCP/技能**（以为没有），也让人低估项目成熟度。
  这是"反向的声称与实现不符"，同样属于诚实性问题。

### S3【已核实】状态权威三足鼎立、互相打脸
- **证据**：
  - `PRODUCT-GOAL.md:4` 自称"与 PLAN 冲突时以本文为准"，但其 §6 进度表（`:130-147`）停在 2026-09-18：
    W6–W23 大片"未开始"，还写"当前规模 10 个测试文件 / 149 个测试"（实际 36 个文件 / 598+ 测试）。
  - `COVERAGE-MATRIX.md:6` 核对时间 2026-09-18，状态列大量 `⏳ W6/W7/W8/W23`（均已完成）；
    但 `PRODUCT-GOAL.md:37` 又把它指定为状态权威。
  - `PROGRESS.md` 自称门禁唯一口径，**自身内部也矛盾**：`:31` 说 W23 外观已完成，`:74` 把"W17 主题与背景（并入 W23）"列在"未开始"；`:36-38` 说 W11a-c 已落地，`:70` 又把 W11 列在未开始。
- **影响**："项目做到哪了"这个问题**没有可信答案**；外部评审与我自己下一轮判断都会基于错信息。

### S4【已核实】PLAN 的两条 ADR 级约束从未兑现，也没标注
- **证据**：
  - `PLAN.md:83` `Agent 执行位置 | utilityProcess（main 只路由）`；全仓 `grep utilityProcess` **零命中**，
    实际 Agent Loop / 工具执行 / SSE / MCP 全在 main 进程（`chat-service.ts`、`ipc.ts`）。
    而 `COVERAGE-MATRIX.md:14` 仍写"四进程模型…**文档与代码一致**"。
  - `PLAN.md:362` 要求 `main ≤300 行`；实际 `ipc.ts` **565 行**、`mcp-service.ts` 511 行；
    ESLint 只有 800 行一条（`eslint.config.js:27`），**没有 main 专属规则**。
- **影响**："main 只路由"的性能前提不成立（重负载压在主进程事件循环上）；
  承诺未兑现且被标成"一致"，是**图纸与现实脱节的典型**。

### S5【已核实】里程碑编号 M3/M4/M5 在不同文档指不同东西
- **证据**：`PLAN.md:200-211`（M3=聊天UI、M4=工具权限、M5=Agent Loop）与
  `PLAN.md:237-260`（M3=学习闭环、M5a=画布浏览器）**同一文件内**两套；
  `PRODUCT-GOAL.md:107-111`（M3=内置浏览器、M4=无限画布）；`PROGRESS.md:79`（缺口 = M3 浏览器 · M4 画布）。
- **影响**："哪个里程碑没做""依赖是否满足"无法判定 —— 而 PLAN 的防膨胀机制（严格按周表交付）正是建立在编号之上。

### S6【已核实】PERF-BUDGET 整篇内容重复两套，两套数据还打架
- **证据**：`docs/PERF-BUDGET.md` 出现**两次** `## 一、启动性能`（`:24` 与 `:96`），
  章节编号、实测值（536/562/632ms vs 466ms）、体积（652KB vs 683KB）两套并存。
- **影响**：性能回归的判定基准不存在；且 README `:133` 仍写"有回归待修"，而 PERF-BUDGET 自己已声明该回归"被证伪并撤销"。

### S7【已核实】`check:docs` 的盲区，让上面这些漂移**永远绿**
- **证据**：`scripts/check-docs.mjs` 的扫描范围是 `README.md` / `CONTRIBUTING.md` / `SECURITY.md` / `docs/*.md`，
  **不含 `CHANGELOG.md` 与 `review/`**，也**不校验 PROGRESS 里的测试数与 e2e 步数**（只校 README 的）。
  于是 PROGRESS 写"34 个测试文件 / e2e 12 步"（实际 36 / 13）而检查器 8/8 全绿。
- **影响**：**"检查通过"给了假的安心** —— 与我在 W11a/W11b 反复抓的"自引用断言、用例抹平差异"是同一类病。

## 五、隐患主题（不是单点问题，是"楼"的结构性问题）

1. **状态源分散**：5 份文档各说各的进度 → 必须有**唯一权威**，其余改为指针（本报告与 `docs/TRACK-PLANS.md` 已确立处置方向）。
2. **检查器盲区**：`check:docs` 只覆盖它自己写过的范围，"绿"不等于"真一致" → 要**扩范围**（PROGRESS 数量、CHANGELOG、review/）。
3. **"写下来 ≠ 做到"**：PLAN 的 ADR 与工程约束没有兑现也没有标注 → 要么做，要么**如实标注为未完成**（这两种都可接受，装没做才不可接受）。
4. **同一概念多处维护**：权限模式、文案、默认值、里程碑编号 → 一律**收敛到单一来源**。
5. **旧的"未接线能力"堆积**：git 写操作、记忆写入、疲劳提示 —— 声明了却没人能用，会持续误导读者判断能力边界。
