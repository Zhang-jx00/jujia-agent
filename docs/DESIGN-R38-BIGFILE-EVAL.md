> **这一页是评估稿，不是实现**：**一行产品代码都没动**，只把"该不该拆 / 切哪个口子 / 代价 / 回归面"算清，
> 让下一轮（或所有者）能照着拍板。

## 零、先把题面前提核一遍（这一节的结论改写了 R38 的题面）

R38 的题面是"评估大文件拆分"。**动手前现扫，第一件事就是发现题面前提已经不成立了**：

### 0.1 R20 登记时用的是什么口径？—— **物理行**

R20（`v0.73.0-规整13`，2026-10-13）原文（`docs/CHANGELOG-ARCHIVE.md:5049`）：

> 大文件（`ChatPanel.tsx` 917 行 / `CanvasPanel.tsx` 610 行 / `McpPanel.tsx` 484 行）
> **不在清理轮拆**，登记为结构性候选。

**那三个数字是物理行数**（含空行与注释）。

### 0.2 但真正会拦人的判据是 eslint 的 `max-lines` —— **跳过空行与注释**

`eslint.config.js:39`：

```js
'max-lines': ['error', { max: 800, skipBlankLines: true, skipComments: true }],
```

⇒ **"逻辑行"才是判据，物理行不是。**
**本仓口径（自 R38 起，所有行数一律按这个口径写）**：
**行数 = eslint 的 `max-lines` 口径（`max: 800`、`skipBlankLines: true`、`skipComments: true`）** ——
即**跳过空行与整行注释**后的行数。**报行数时必须报这个口径，并注明口径**，
否则读者会拿它跟 800 比，而**两个口径差 200~500 行**。

### 0.3 现扫（**eslint 口径**：跳过空行 + 整行注释 + 块注释内的行）

扫全仓 **317 个 ts/tsx**：

| 文件 | 物理行 | **eslint 口径** | 距 800 还差 |
|------|-------:|----------------:|-------------:|
| `packages/shared-ipc/src/contracts.ts` | 1314 | **792** | 8 |
| `apps/desktop/src/main/chat-service.ts` | 1124 | **782** | 18 |
| `apps/desktop/src/renderer/src/features/chat/ChatPanel.tsx` | 977 | **774** | 26 |
| `apps/desktop/src/preload/index.ts` | 803 | **590** | 210 |
| `apps/desktop/src/renderer/src/features/canvas/CanvasPanel.tsx` | 656 | **553** | 247 |
| `apps/desktop/src/renderer/src/features/mcp/McpPanel.tsx` | 485 | **426** | 374 |

**超过阈值 800 的文件：零个。**

### 0.4 三条结论

① **"三个候选超阈"这个前提是错的** —— 那是**物理行**口径的产物。
`ChatPanel.tsx` 物理 977 行（比 R20 登记时还多 60 行），**逻辑行只有 774**，**离阈值还有 26 行**。
`CanvasPanel.tsx` / `McpPanel.tsx` 更是 553 / 426，离得很远。

② **"没有文件超阈"不等于"没有风险"** —— 三个文件**贴着阈值**（792 / 782 / 774，差 8~26 行）。
下一轮随便加几段注释/代码就会撞线，**撞线那天是 lint 当场拦**（这正是 `max-lines` 存在的意义）。

③ **R38 的题面要改写** —— 从"评估**要不要拆**"改成"评估**在撞线之前拆哪一口**"。

> **一条方法论教训（与 R36 那条"别拿上一轮的口头数字当事实"同源）**：
> **"文件有多少行"这个问题有两个答案**（物理行 / 逻辑行），
> **必须先问"哪个答案才是判据"** —— 本仓的判据是 eslint 的口径，R20 记的是物理行，
> **两者差 200~500 行**。用错口径 ⇒ 结论整个反过来（"超阈、该拆" vs "没超阈、别拆"）。

## 一、R20 登记的那三个候选，现在各自是什么形状？

### 1.1 `ChatPanel.tsx`（774 逻辑行 · 差阈值 26 行）

**它已经不是 R20 时的那个文件了** —— R20 之后它被**切过一次**
（`v0.78.0-扩容5`：`ChatPanel 行数触顶 → 切出 use-attachments.ts + ChatComposer.tsx 两个文件`，
见 `docs/PROGRESS.md:45`）。

**现扫它的构成**（看"什么在里面"决定"还能从哪切"）：

| 部分 | 性质 | 切出去的话会怎样 |

| 会话/连接选择、**在流状态**、历史恢复、翻页 | 状态与生命周期 | 抽走要搬一堆 state ⇒ **回归面大** |

## 二、`contracts.ts`（792 · 差 8 行）—— 该切吗？

### 2.1 事实

- 它是 **`packages/shared-ipc`** 的契约层：zod schema + 通道常量 + `DONE_END_REASONS` / `PERMISSION_EXPIRED_REASONS` 那种**穷举常量表**。
- **它已经被切过一次**：`v0.86.0-加固18` 里"`contracts.ts` 被 `max-lines` 800 当场拦住 ⇒ **拆出 `contracts-tool.ts`，没放宽阈值**"
  （`docs/PROGRESS.md:47`）。**这是本仓的既有先例：撞线就拆，不抬阈值。**

### 2.2 差 8 行 ⇒ **下一个功能点就会撞线**

`max-lines` 撞线是**当场红**（CI 门禁）⇒ 撞线那天必须当场处理。
而"当场处理"的成本是**急就章的拆**（在赶 CI 的压力下拆）⇒ **不如现在评估**。

### 2.3 切哪个口子？（三个候选，按代价排）

| 方案 | 切什么 | 代价 | 回归面 |
|------|--------|------|--------|
| **A（推荐）** | **契约按"域"切**：`contracts-tool.ts`（已切过一次）之后，把**会话/记忆/任务/画布/日志**那几族各自成文件 | 低 —— 纯 zod schema，**无运行时状态**；导出面不变（barrel 重导出） | **极小**：契约层没有行为，改名不改语义；`contracts.test.ts` 与各处 import 跑一遍即可 |
| B | 切**穷举常量表**（`DONE_END_REASONS` 那种）出去 | 低 | 小 |
| C | 切**通道常量**（`channels.ts` 已独立，**别动**） | — | — |

**推荐 A**。理由：**它差 8 行且纯声明** —— 这是"拆得最省力、回归面最小"的那种撞线。

### 2.4 但**本轮不拆**

R38 的题面是"**只评估不动刀**"，且拆契约要动**导出面**（`packages/shared-ipc` 是三个包共用的）⇒
**归到下一轮**（见 §五）。

## 三、`chat-service.ts`（782 · 差 18 行）—— 比 `contracts.ts` 难

### 3.1 事实

它是主进程聊天服务：**会话装配 / 工具执行 / 流式 / 落盘 / 压缩**都在里面。

**它也被切过**：R27（T43）动过它、`chat-honesty-wiring` 那些源锁盯着它、
T47 那条"count 锁"就落在它里面（`console.warn` 只许剩 2 处）。

### 3.2 为什么它比 `contracts.ts` 难

| | `contracts.ts` | `chat-service.ts` |
|---|---|---|
| 性质 | **纯声明**（zod schema / 常量） | **有状态、有副作用**（会话、落盘、工具执行、流） |
| 拆开的风险 | 几乎为零（改名不改语义） | **高**：切错 ⇒ 状态漏搬 / 副作用顺序变 |
| 回归面 | 契约层测试 + import 面 | **e2e 全流程 + 那些源锁**（源锁是**按文件路径**写的 ⇒ 拆文件 ⇒ **锁的 needle 要跟着改**，否则"锁还在但盯的是旧路径"） |

**这条"源锁跟着拆改"是本仓反复吃亏的地方**（R27 的 T44 写死四个文件名、
R35 的 M7 切片窗口被合法增长养瞎）⇒ **拆 `chat-service.ts` 的真实代价主要在这里**。

### 3.3 切哪个口子？

| 方案 | 切什么 | 代价 | 回归面 |
|------|--------|------|--------|
| A | 切**会话装配**（headParts / hydrate / 压缩那一族） | 中 | 中（落盘与压缩都碰状态） |
| B | 切**工具执行桥**（toolRun 的入参校验与调用转发） | 中 | 中 |
| C | 切**流式装配** | 低 | 中（流事件顺序敏感） |

**本轮不给"切哪个"的结论** —— 理由在 §四：**这个文件在拆之前需要先有一份"它现在到底承担几件事"的现扫账**，
而那份账**不是本轮该做的**（本轮是评估大文件，不是给 `chat-service.ts` 做解剖）。

⇒ **`chat-service.ts` 的结论是"需要单独一轮做解剖，再定切口"**，不与 R38 混在一起。

## 四、T57③ 的评估结论：`child-process-gone` 处理器要不要加？

### 4.1 原始登记

T57③ 原文（`docs/TRACK-ROADMAP.md:184`）：

> ③ 全仓**没有 `child-process-gone` 处理器**（`render-process-gone` 有，T38 修的）。

R31 当时的判断是：**"这与 utilityProcess 迁移是同一题，是架构决定不是缺陷"** ⇒ 登记为评估项。

### 4.2 复核：`child-process-gone` 到底会为谁触发？

**现扫本仓主进程实际会起的子进程**（`grep` 全仓 `child_process.fork` / `utilityProcess` ⇒ **零命中**）：

| 子进程 | 怎么起的 | 归谁管 | 崩溃了会怎样 |
|--------|----------|--------|------------|
| **MCP 服务端** | `stdio-transport.ts:175` `doSpawn(..., stdio: ['pipe','pipe','pipe'])` | 主进程 `mcp-service` 持有 session | **已被覆盖**：`child.on('exit')`（`:196`）→ `reportExit`（`:198`）→ 上层 `handleExit` 摘工具 + 结束挂起请求 |
| **内置终端 PTY** | `terminal-service.ts:180` `pty.spawn` | 主进程持有 `IPty` | **已被覆盖**（会话归属工作区 + 窗口关闭/应用退出时杀掉所有 PTY） |
| **用户选的外部程序** | `open-with-launch.ts:42` `spawn(exePath, ..., detached, stdio:'ignore')` | **不归本应用管**（一次性、`detached`） | **不该管**（那是用户的程序，崩了与我们无关） |

### 4.3 结论：**不加**

三条理由，逐条是**现扫出来的事实**而不是推演：

① **本仓没有 `utilityProcess`、没有 `child_process.fork`** ⇒
**`child-process-gone` 这个 Electron 事件在本仓的主要触发源根本不存在**。
（`child-process-gone` 是 `utilityProcess` 专有的 —— 知识库卡片 F5 明确记着：
`serviceName` "will appear in… `child-process-gone` event of `app`"。）

② **已经在管的两个子进程都已被覆盖**（上表）——
MCP 走 `child.on('exit')`、终端走 PTY 自己的生命周期。**再补一个 `app.on('child-process-gone')` 只会重复报同一件事。**

③ **第三个（用户选的外部程序）不该管** —— 那是用户的程序，`detached` 且 `stdio:'ignore'`，
它崩了**与本应用无关**；去"处理"它反而是**替用户决定**（本仓对终端的同类口径：
"归属不明的进程一律不杀"）。

### 4.4 那 utilityProcess 迁移要不要做？

**不做**（本轮给结论，不是"待评估"）：

- 本仓**不需要常驻的 Node 子进程** —— 三个子进程来源全是"起一次、用一次、或用户自己挑的"；
- 知识库 F5 给 utilityProcess 的建议是"**host the agent runtime / tool runner / LLM session loop**"——
  **本仓的 agent loop 跑在主进程**（`packages/agent-core` 是同进程库，不是子进程），
  **没有"要把 agent loop 搬进子进程"的需求**；
- 迁移的成本很高（生命周期、崩溃归属、IPC 形态、asar 打包都要重验）⇒
  **为一个不存在的需求付这个代价，是典型的"为了将来"**。

⇒ **T57③ 的结论：关闭（不做），不占队列。**
**理由写进台账**：不是"忘了做"，是"现扫证明不需要做"。
