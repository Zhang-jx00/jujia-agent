## 一、为什么单独立项（停牌①）

生成一张图的请求会把**提示词（可能还带一张底图）发给远端服务商**，拿到**图片字节**落回本机。
这一步同时碰到**两个已经定过的东西**：

1. **出站语义** —— 现役表述是「除**你主动发起的模型请求（文字 / 图片）**外，数据不出本机」
   （README §1 · SECURITY「数据会离开这台机器吗」）。生成请求**是不是**这句话已经覆盖的"模型请求"，
   取决于它**打给谁**（见 §二）—— 这一层必须说清，不能含糊过去。
2. **落盘语义** —— R14 批的是「**附件不落盘**」（图片只是"给模型看"的输入）。而生成的图是**产物**
   （用户要的是文件），**方向正好相反**。仓里已有两条现成惯例可以对照（§六）。

## 二、先把话说清：冲突到底在不在？（本稿最要紧的一条）

**不冲突的那一支（表述可复用）**：生成请求**发往当前连接配置的服务商**，输入是**文字提示词**
（外加可选的一张底图）—— 那它就是 README §1 那句话里的「**你主动发起的模型请求（文字 / 图片）**」，
**表述已经覆盖**，**不需要新的表述批复**。

**冲突的那一支（表述要改）**：生成请求打往**另一个服务商 / 另一把 key**（例如某家的视频 API
与当前聊天连接不是一家）—— 那"当前连接"这四个字就盖不住了，README「出网只有两处」、
SECURITY 出站表都要加行，**属停牌①**（出站语义变更），须所有者拍板。

⇒ **所以本项目的真实问题不是"要不要改表述"，而是"生成走哪条通道"**：
**走当前连接 ⇒ 零表述改动**；**走别的服务商 ⇒ 一次表述批复 + 出站表新增行**。
§四的选项就是按这条分叉给的。

> **一条要补的边界（第二遍复核时才发现的）**：R14 批的是「**附件不落盘**」——
> 那是**本机**的口径（会话 jsonl / 长期记忆 / 审计正文都不写字节）。
> **提示词会不会留在服务商那边（生成历史 / 画廊 / 训练留存），本项目管不了** ——
> 那是**服务商的政策**，我们只能**如实说明**，不能承诺"不留在那边"。
> ⇒ 界面文案要说的是「**本机不留副本**」，**不许说成"没人存你的提示词"**。
> 这一条同样适用于 R14 的图片输入（当时没写这层，本轮补上）。

## 三、范围候选（按"零依赖 / 要装依赖 / 本机不可行"三档分）

| 候选 | 做什么 | 零新依赖？ | 工程量 / 成本 | 产物 | 备注 |
|---|---|---|---|---|---|
| **S1 文生图** | 提示词 → 一张图 | ✅ **可以**（OAI 兼容 `POST /images/generations`，HTTP + JSON） | 小 | 图片字节 | **provider 层现成**：`resolveEndpoint(baseUrl, path)` 与注入式 `fetcher` 都在，加一路 path 即可 |
| **S2 图生图 / 编辑** | 一张底图 + 提示词 → 一张图 | ✅ 可以（同上，`multipart` 或 base64 入参） | 中 | 图片字节 | **入站字节与 R14 同族**（要过魔数 / 5MB / 剥 EXIF 那道门） |
| **S3 视频生成** | 提示词 → 一段视频 | ✅ 可以（HTTP + JSON：提交 job + 轮询） | **大**（异步长任务、分钟级、几十 MB、成本高） | 视频文件 | 仓里已有长任务基建（`task-state` / 断点续跑），但**"长耗时 + 大文件 + 计费"三件事叠在一起**，不是"再加一路 fetch" |
| **S4 音频 / 语音** | TTS / ASR | ✅ 可以 | 小–中 | 音频文件 | 与 M11 的"多模态"主题**弱相关**，建议**不并进这一批** |
| **S5 本机生成** | 本机跑扩散模型 | ❌ **要装依赖**（Python 推理栈） | 极大 | 图片 | **本轮否掉，不进选项** —— 理由是**算力与依赖**，不是"下不到"：**本机只有 AMD Radeon 780M 集显**（4GB 显存；`nvidia-smi` 不存在 ⇒ 无独立 GPU），扩散模型的常规本机推理不现实；模型源**现在实测可达**（`huggingface.co` HTTP 200）⇒ 真正的门槛是那套推理栈（**停牌②**）+ 算力 |

> **"零依赖"的准确说法**：**不加任何 npm 包**。HTTP 与 JSON 用 Node 自带 `fetch`，
> provider 层已经是**注入式 `fetcher`**（`deps.fetcher ?? fetch`）⇒ 测试里能塞假远端。
> **不需要官方 SDK** —— 官方 SDK 只在"厂商专有、非 OAI 兼容"时才必要，那属于 §四 的 C 档。

## 四、选项（供拍板；**推荐值加粗**）

| 选项 | 含义 | 代价 / 前提 |
|------|------|-------------|
| **A. 维持定位，媒体生成不做** | 把 M11 剩余**永久**划出边界：README 能力表那行「媒体生成（多模态另一半）」改成"**不做**"，不再留悬念 | 放弃"让它画一张图给我看"的能力；口径要一次性改准（**现在那行写着"未开始"，是悬念不是决定**） |
| **B. 只做 S1 文生图，走当前连接（推荐）** | 在**当前连接**上发 `POST /images/generations`（OAI 兼容），提示词与可选底图都发往该连接 ⇒ **表述零改动**；产物落**本应用数据目录**（照画布的惯例，不过权限门） | 需要：① 产物落盘口径写清（§五-2）· ② 供应商差异兜底（有的连接没有这个端点 ⇒ **如实说"这个连接不支持生成"**，不静默失败）· ③ 成本上限（一次生成多少钱、多长时间，界面要事先说）· ④ 假远端测试面 · ⑤ **S2/S3 另起一轮**（它们各有各的账） |
| C. 一次做完 S1–S3（含视频、含别的服务商） | 媒体生成全家桶 | **要装依赖**（厂商官方 SDK）⇒ **停牌②**；且**视频那一支的成本与时长**需要一个产品决定（"一次生成能花多少钱"不是工程问题）；**表述要改**（别的服务商 ⇒ §二 的冲突那一支）⇒ **停牌①**。**本轮不建议** |

> **推荐 B 的理由**：它是唯一**不撞任何一条停牌、又真的把能力交出去**的选项 ——
> 走当前连接 ⇒ 不动出站表述（§二）；用 Node 自带 fetch ⇒ 不装依赖；
> 落本应用数据目录 ⇒ 不改权限语义。**它同时是"最小可撤"的一档**：真做完了发现没人在用，
> 撤掉只影响 S1 一个能力面，而 C 那一档撤不干净。

## 五、若选 B：先决清单（做之前必须先补，缺一不做）

1. **产物落盘口径**（本稿最需要拍板的一条）：落在**哪**、**叫什么**、**留多久**。
   仓里两条惯例可直接选：
   - **照画布**：落在本应用数据目录（`canvasDir` 一类），**不过权限门**（它写的是本应用自己的数据）；
   - **照 IDE**：落进**用户工作区**，**走工具那扇门**（软确认）。
   ⇒ **本稿建议前者**（生成的图是本应用自己的产物，不该占用用户的工作区、也不该为它加一道门）。
   —— **【R51 已落地】** 落 `join(getDataRoot(), 'generated-images')`；**不过权限门**；原子写（tmp→fsync→rename）。
2. **"这个连接不支持生成"要有话可说**：OAI 兼容是**事实上的**标准，不是所有实现都有 `/images/generations`
   ⇒ 端点缺失 / 4xx / 超时**各有各的一句话**，**不许静默失败，也不许显示成"生成成功"**。
   —— **【R51 已落地】** 失败分类落成 `MediaImageFailReason`（`unsupported` / `url_only` / `too_large` / `not_image` / `bad_response` / `http_error` / `network_error` / `timeout` / `no_connection` / `write_failed`），界面逐类显示。
3. **成本与时长上限**（界面要事先说）：一次生成的**张数 / 时长 / 大小上限**，超了要**说清是哪个上限挡住的**。
   —— **【R51 已落地】** 张数 ≤ 4、尺寸固定 `1024×1024`、单张 ≤ 5MB、单次 ≤ 120 秒 —— 四条都在面板上**事先**写出来；超限时回执指名"是哪个上限挡住的"。
4. **入站字节照 R14 那道门**：若支持 S2（底图）⇒ 魔数判定 · 5MB · 剥 EXIF **复用现成那道**（`media/image-prep.ts`），**不另写一份**。
   —— **【R51 本轮不适用】** S1 **没有输入图片**，没有入站字节；本轮要管的是**回程**字节 —— 复用的**正是**同一道门里的 `sniffImageMime` + `IMAGE_MAX_BYTES`（**不另写一份**）。剥 EXIF 那一步本轮**不**做（产物是服务商给的，不含本机拍摄元数据；S2 若做底图再议）。
5. **出站表加行**（SECURITY）：加"模型 API"那一行的**生成子项**（同一目标，但要把"生成请求"这半句说清）；
   **README 的「出网只有两处」不用改**（还是同一个服务商）。
   —— **【R51 已落地】** `SECURITY.md` 出站表**只加一行**（"同一模型 API 的生成子项"）；**README.md 零改动**。
6. **测试面**：远端类功能**不能只靠本机单测**（`DECISION-REMOTE.md` §四-6 的先例）⇒ 先做一台
   **假远端**（本地 HTTP 服务扮演 `POST /images/generations`），e2e 断言三层真值：
   **服务端收到的提示词字节 / 落盘产物字节 / 界面那句回执**。
   —— **【R51 已落地】** 假远端（`node:http`）在三处真跑：provider 层 / 服务层 / e2e。e2e 断言：服务端收到的提示词字节 · 落盘产物的**逐字节**一致 · 界面那句回执。
7. **判定语义零改动**：生成**不是工具调用**（与 R14 的图片输入同一口径：对话发送不进执行审计那本账），
   **不要顺手把它塞进权限门**——那会把"我请你画张图"变成"每次画图都要你点一次确认"。
   —— **【R51 已落地】** `ipc/media.ts` **刻意没有**调 `ctx.permission` / `ctx.audit`，**没有**新增审批弹窗；既有判定（权限 / 审批 / 路径守卫）**一字未改**。

## 六、现状与关联（如实，不加想象）

- **provider 层现在只有两路**：`resolveEndpoint(baseUrl, 'chat/completions' | 'models')` ——
  **没有任何图片 / 视频 / 音频代码**（全仓 `providers/` 目录里 `image / video / audio / generation` 四个词零命中）。
  ⇒ S1 的真实成本是"**加一路 path + 一份契约 + 一个入口**"，不是"接一个 SDK"。
- **契约层没有媒体产物**：`contracts.ts` 里只有 `chatImageInputSchema`（**输入**）与 `imageCount`（计数），
  **没有"生成产物"这种形状** ⇒ 要新立。
- **两条落盘惯例都在**（§五-1）：画布图落本应用数据目录（不过门）· IDE 文件落工作区（过门）。
- **本机生成不现实（理由要写准）**：本机**只有 AMD Radeon 780M 集显**（4GB 显存，`nvidia-smi` 不存在 ⇒ 无独立 GPU），
  且要另装一整套推理栈（**停牌②**）⇒ S5 不进选项。**注意**：模型源**现在实测可达**（`huggingface.co` HTTP 200，
  2026-10-21）—— 早前"下不到模型"那条理由**已经不成立**，别再拿它当挡箭牌。
- **与 M20–M22 的关系照旧**：本稿**不依赖** `DECISION-REMOTE.md` 的拍板结果（§一）。
- **与 M14 的关系**：无交叉（M14 是多子 agent 编排，不含媒体能力）。
