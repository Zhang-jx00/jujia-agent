# M17 批一 · 长任务与断点续跑（R15）· 设计口径

> 轨道原文（`docs/TRACK-ROADMAP.md` R15 行）：任务状态机（进行中 / 被打断 / 可续）+ 崩溃恢复，
> **复用 `json-store` 与 `will-quit` 那套已验证的写盘时序**（不与 M6 会话持久化分叉、不另起一套存储）；
> 恢复时**如实说"上次断在第几步"**，不假装无缝；**硬约束：续跑不得绕过权限门重放高副作用动作** ——
> 重放到那一步就重新问。与 **T42**（"长命令转后台"）同批定口径。
> 本文件是工程设计与边界记录（本批无停牌项：不改已批的安全语义、零新依赖、不与 M14/M19 冲突）。
>
> **交付记录（2026-10-13，R15 → `v0.79.0-铺设16`）**：§一 四条判据全部落地（实现位置见 PROGRESS 铺设16 行）；
> e2e [60] 以三层真值收口（崩溃现场 task.json / 读时判定与卡片 / **续跑时审批弹窗再次出现**）；复核 075。
> **设计之外补上的一格**（实现中核复发现）：起轮也要补写一次**会话元信息** —— 半途崩溃的轮次走不到
> 轮末 flush，没有它重启后在会话清单里根本找不到恢复卡片。

## 一、批一判据（做完什么算完成）

1. **任务状态机**：每轮对话起轮时在**该会话目录**写一条任务记录（`task.json`，JsonStore 原子写）；
   完成一个工具记一步；轮末按结局置 `done / failed / aborted`。
2. **崩溃恢复**：下次读到该会话时，凡是状态仍为 `running` 的记录 = 上次进程被崩溃/强退带走 →
   **读时判定**为 `interrupted` 并写回；界面显示"上次断在第几步"与「续跑 / 不再提示」。
3. **续跑**：从**唯一入口**（`ipc/turn-trigger.ts` 的 `startTurn`）进；原始要求与已完成步骤
   经系统提示注入段交给模型（**一次性**，只在该续跑轮生效）；用户点「续跑」本身是人的动作，
   界面出现一条真实的用户消息（文案常量同源）。
4. **硬约束（权限门）**：续跑**不重放任何动作** —— 步骤清单是给模型"别重做"的提示，不是执行回放；
   模型为继续任务新发起的任何工具（尤其 `run_command` 这类执行类）照旧经过同一扇门重新问。
   结构上成立（模型不可能绕过 `runTool`），并用 e2e 做正面证据：续跑时审批弹窗**再次出现**。

## 二、任务记录（存哪、写什么、何时写）

- **位置**：`sessions/<id>/task.json`（会话目录内，**唯一入口 `sessionDir()` 白名单照旧生效**）——
  与会话同生共死、随会话目录一起被搬走；**不另起存储**，用 `packages/shared/src/json-store.ts`
  的 `JsonStore`（envelope + tmp→fsync→rename + `.bak`），与 `session.meta.json` 同一套写法。
- **只留最近一条**（批一边界）：用户新发一条消息 = 开一个新任务并**整体覆盖**上一条
  （上一条若还是 `interrupted` 未处理，被覆盖即消失 —— 如实记进本文档，不做多任务历史）。
- **字段**（`task-state.ts` 的类型即判据）：
  `taskId / sessionId / instruction（用户原话）/ status / startedAt / updatedAt / stepsDone（完成步数）/
  recentSteps（最近 ≤12 步 {name, ok, at}）/ runningStep（此刻正在跑的工具名，若有）/
  finishedAt / interruptedAt / resumedAt / resumeCount`。
  `instruction` 是用户自己发过的内容，与 `messages.jsonl` 同一敏感级；**它就存在会话目录里**。
- **何时写**（全部经 JsonStore，串行化由它保证）：
  ① 起轮（push 用户消息后、`runAgentTurn` 之前）→ `running`；**这一步在模型还没被调用时就落盘**，
  所以"第一轮就在等模型时崩溃"也能恢复；**同一拍补写一次会话元信息**（`saveMeta`）——
  崩溃的轮次走不到轮末 flush，少了这一格，重启后清单里连这个会话都列不出来（恢复卡片无从谈起）；
  ② `tool_start` → 记 `runningStep`；`tool_end` → `stepsDone+1`、`runningStep` 清空；
  ③ 轮末（`finally`，与 `flushSession` 同一拍）→ 按结局置 `done/failed/aborted`。
  写失败**不抛穿业务**（任务记录坏了不该让一次正常对话跟着死），但失败计数进日志。

## 三、状态机

```
                ┌──────────── 崩溃 / 强退（记录留在盘上）────────────┐
起轮 running ──┬─→ done（正常答完）
               ├─→ failed（loop_error / max_turns / 上游截断）      │
               ├─→ aborted（用户点停止）                             │
               └─────────────────────────────────────────────→ interrupted（读时判定 + 写回）
interrupted ──→（点「续跑」）resumed──→ running（同一 taskId 继续记步）→ done/failed/aborted
interrupted ──→（点「不再提示」）dismissed（从此不再弹这张卡）
```

`interrupted` 的判定条件只有一个：**被读到时状态还是 `running`**（进程内活跃任务不会被读到判定，
因为同一会话的读都发生在没有在跑的时候）。判定动作本身要写回盘（幂等：已 interrupted 的不重写）。

## 四、"断在第几步"的如实语义

- "已完成 k 步"= 已收到 `tool_end` 的工具数；`runningStep` 非空 → 如实说"中断时正在运行 <工具名>（结果未落盘）"；
- **半截回答不落盘**（本仓铁律：轮末才落盘），所以卡片如实写"中断前那次回答没有留存"，
  不给"假装还在"的错觉；
- 原指令之所以要单独存在任务记录里：**崩溃轮的 messages 一条都没落盘**（整轮只在轮末 flush），
  没有它，"续跑"就不知道要续什么 —— 这不与 M6 分叉，只是把 M6 已在会话目录里的东西补一格元数据。

## 五、续跑机制（唯一入口 + 一次性注入）

- 界面「续跑」→ `CHAT_TASK_RESUME(sessionId)` → 主进程校验（记录存在且为 `interrupted`；会话不在跑）
  → **走 `startTurn`**（与用户敲字、定时到点完全同一条入口）多带一个 `resumeTaskId`；
- `sendMessage` 在该轮：把可见的用户消息（`RESUME_USER_TEXT`，constants 在 `shared-ipc` 单源）
  照常 push 进历史；任务记录置 `resumed`（`resumedAt`、`resumeCount+1`，随后同轮回到 `running`）；
- **注入段**（`agent-core/src/context/task-resume.ts` 纯函数产出，格式同 `buildSummarySection` 的出处风格）：
  ```
  ## 被中断的任务（续跑，来源：sessions/<id>/task.json）
  上一轮任务在应用退出/崩溃时中断（不是模型答完）。用户当时的原始要求：「…」。
  已完成 k 步：① run_command ✓ ② …；中断时正在运行 run_command（结果未落盘）；中断前那次回答没有留存。
  请从中断处继续完成这个任务；已完成的步骤**不要重做**；有副作用的动作会再次向用户确认。
  ```
  注入进系统提示（`assembleSystemPrompt` 新增可选层 `taskResume`，排在摘要段之后）；
  **只在带 `resumeTaskId` 的那一轮注入** —— 系统提示本来每轮重装配，不加持久段就自然消失。
- 权限门：模型继续任务时重发的 `run_command` 走 `runTool → decideGate`，**照旧硬 ask**；
  「总是允许」是会话内存级、重启即空 —— 续跑天然重问。e2e 断言之。

## 六、T42 口径（同批裁定，不改既有结论）

**"模型驱动的长命令转后台"仍然不做**（理由见 `TRACK-ROADMAP.md` T42 行：要么把半截输出当完整=撒谎，
要么重造终端那套 pty 生命周期=重复）。本批把 T42 从"待排"钉成"已定口径"：
长任务的**可见性与断点**由本任务状态机承载；**"跑完之后把结果交回给那一轮"这个课题不实现**——
真要做，必须复用同一套任务状态机（任务身份 / 结果过期 / 期间用户又发一轮 / 审批算哪一次的四个问题
在本文档 §二、§五 已有判据锚点）。用户手驱动的内置终端继续作为交互式长任务的既有承载。

## 七、批一明确不做（边界）

多任务历史（只留最近一条）· 会话列表徽标（卡片只在打开该会话时出现）· 自动续跑（必须人点）·
中途轮次增量落盘（轮末落盘铁律不动）· 半截回答的持久化 · 子代理/编排（M14 归口后另议）·
把任务记录写进 `messages.jsonl`（**记录与消息分家**，同 summary.md 的理由）。

## 八、测试面

- **纯层**（vitest）：`task-state.ts`（状态转换 / 步数 / 读时判定幂等 / 摘要文案）、
  `agent-core/context/task-resume.ts`（注入段：含原指令与步骤、空步骤的说法、不注入=返回空串）；
- **接线锁**：续跑只能经 `startTurn`（`ipc/chat.ts` 的 resume handler 调它；`chat-service` 的
  resume 分支不直呼 `runAgentTurn`）；任务记录只经 JsonStore（不许 `appendFile` 写 task.json）；
  续跑路径不得触碰 `alwaysAllow`（硬约束的结构证据）；
- **e2e [60]**：起一条慢命令轮 → **跑到一半关闭应用**（真实退出路径）→ 重启 →
  卡片如实说"已完成 0 步 / 正在运行 run_command" → 点「续跑」→ **审批弹窗再次出现**（硬约束正面证据）
  → 批准 → 跑完 → 任务记录 `done`；磁盘断言 `task.json` 的字段与状态。
