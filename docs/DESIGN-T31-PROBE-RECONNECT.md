## 一、先把现状钉住（现扫，不是回忆）

### 一.1 我们今天"知道"什么

| 事 | 现在怎么知道 | 证据 |
|----|------------|------|
| 服务端**进程死了** | `onExit` 回调（`stdio-transport.ts:79`）⇒ 落 `state='exited'` | `mcp-service.ts` 的 `handleExit` |
| 服务端**僵而不退**（进程在却不应声） | **靠一次调用超时**才暴露 —— `recordCallFailure` 只在 `failure === 'transport'` 时把状态改成 `error` | `mcp-service.ts:506-521` |
| 服务端**还能用** | `state === 'connected'` | `mcp-service.ts:472` |

### 一.2 那个 `alive` getter 到底有没有用

`stdio-transport.ts:217` 有一个 `get alive()`：进程还在、没退出、没被 `dispose` 就返回 `true`。

**现扫它的全部消费方**（`grep '\.alive\b'`）：

- `mcp-e2e.test.ts:185 / 193`
- `stdio-transport.anomaly.test.ts:29 / 66`
- `stdio-transport.test.ts:100 / 324 / 330`

**全是测试**。**生产代码零消费** —— 它回答的是"**我刚 spawn 的那个 child 还在不在**"，
而**不是**"**这个 MCP 服务端此刻还能不能干活**"。这两个问题在真实世界里会分叉：
进程活着但**不应声**（服务端自己的线程池死锁、它依赖的下游挂了）时，`alive` 仍然是 `true`，
而它**已经不提供服务了**。⇒ **拿 `alive` 当探活是错的**，这一条必须在口径里写死。

### 一.3 "连上了"这件事今天意味着什么

`state = 'connected'` 的唯一来源是**握手成功**（`mcp-service.ts:406`，在 `client.connect()` +
`listTools()` 之后）。**此后没有任何东西会把它改回 `connected`** ——
一次调用失败只把状态改成 `error`（`mcp-service.ts:518`），而 `error` **不区分**"服务端死了"和
"服务端只是这次没答上来"。`exited` 才是"进程真没了"（更精确的事实，`mcp-service.ts:514` 单独认它）。

⇒ **今天的状态字段能说清"死没死"，说不清"现在还能不能用"。**

## 二、口径一：多久没响应算"掉线"？

### 二.1 结论

**不设独立的"掉线"状态。** 我们**不引入后台探活定时器**，理由是成本与证据都不划算：

- **成本**：探一次活的成本与一次真实请求同量级（都是一次 `ping`/一次 JSON-RPC 往返）。
  为"知道它还活着"而常驻地烧这个成本，等于**给每个已连接的第三方进程加一条永久心跳**——
  而心跳本身是**副作用**（服务端可能因此写日志、续租、记账）。
- **证据**："卡住"这件事**本来就是超时才拿得到的**。在没有真实请求的背景下，
  我们没有任何**独立于用户意图**的信号能区分"服务端在忙"和"服务端死了"——
  凭空加一个定时器，只多一处**没人负责的生命周期**（谁来停？应用退出时算不算一次失败？）。

### 二.2 那"僵而不退"怎么算？

**沿用 R6c 已经定的那条，不另起炉灶**：一次调用**什么都没收到**（`failure === 'transport'`）⇒
状态改成 `error` + 记 `lastError` + 广播（`mcp-service.ts:517-520`）。

这条口径的三个要点，**本轮不动它**，只是把它写进这一页让"探活"这件事有个明确的落点：

1. **服务端回了错误（`protocol`）或工具自述失败（`tool`）⇒ 只记原因、不改状态** ——
   那种情况**证明它还在说话**；一个远端工具的普通报错不该把整个服务端标成不可用。
2. **进程已退出（`exited`）不被在途超时盖掉原因** —— 退出码 7 比"请求超时"精确。
3. **不摘工具**：进程还活着时，工具以"不可用 + 为什么"的样子出现，比莫名消失更符合事实。### 二.3 那"多久"这个数字要不要给？

**不给独立的数字阈值**。理由：超时**已经由每次调用的 `requestTimeoutMs` 决定**
（真实 MCP 服务端是 30s，见 `mcp-real-server.test.ts:49`；测试里 8s / 500ms），
我们**不再叠第二套"多久算掉线"的时钟** —— 两套阈值会漂，而且**只有一套能被用户观察到**
（他等的是那次调用，不是某个后台计时器）。

⇒ **一句话口径**：**掉线不是被"测"出来的，是被"用"出来的** —— 用户下一次调用拿到
"当前不可用（状态：error；上次失败：…）"，那一刻就掉线了。

## 三、口径二：要不要自动重连？

### 三.1 结论（R37 当时的结论）：**不做**

> **R47 更新**：所有者已拍板 —— 走**选项 B**（见 `docs/DECISION-SELF-DIRECTED.md`），停牌①解除。
> 下面这段 R37 的理由**一字不改**（它是 B 为什么必须"白名单 + 重新批准"的原因），只是结论变了。

**自动重连 = 在没人点过的情况下重新起一个第三方进程。**
这与本项目安全约定第 3 条（"每次连接都重新征得同意"）**正面冲突**：

- 用户当初点"连接"，批的是**那一次**连接（一次 spawn、一次握手、一次工具批准）；
- 自动重连会在**没有那次点击**的情况下**再起一个进程** —— 而 MCP 服务端能干什么，
  取决于**用户配的命令**（本仓允许配任意 `command` + `args`，见 `mcp-service.ts` 的配置校验）；
- 于是"点过一次"就变成了"**永久授权这个命令被反复拉起**"——
  这与本仓对 `run_command` 的口径（**每次硬 ask**）、对内置终端的处置（**不替用户决定杀哪个**）是同一个方向的。

⇒ **R37 的结论：不做自动重连。**
⇒ **R47 之后：改成"做，但必须逐个服务端显式授权，且重连仍要重新批准"**（选项 B，落地见 §七）。

### 三.2 那"用户想要自动"怎么办

**给一个"用户明确授权的"口子，而不是偷偷替他决定**。R37 只写到"选项"为止 ——
按本仓 §7 的四类停牌，**任何"授权一次、之后自动"的机制都要所有者点头**（它改的是"什么时候可以不问"）。

**R37 留给所有者拍板的那一版长这样**（**当时是选项，R47 之后选项 B 是决定**）：

> **选项 A（现状，默认）**：不自动重连。服务端不可用 ⇒ 状态说清为什么 + 界面上有一个"连接"按钮，
> 用户点一下就走完整流程（**重新走一遍批准**）。
>
> **选项 B（需点头）**：允许**每个服务端单独**勾一个"掉线后自动重连"，
> 但**重连时仍然要走一遍批准**（工具批准**不复用**上一次）——
> 即"自动重连"只免掉"再点一次连接"，**不免掉"再批一次工具"**。
> 且必须是**白名单式显式开启**（默认关），开启时界面说清"这个服务端被授权在掉线后自动重启"。

**B 的边界在哪**（R37 写下的五条，**R52 全部照此落地**）：

- 授权**只对那个服务端生效**，不设全局开关；
- **不跨"应用重启"** —— 应用重启后一切从头开始（此时没有"掉线"这回事）；
- 无限重连**不行**：必须有**上限**（建议 3 次）与**退避**，用尽后停在那儿并说清"试过 N 次没成"；
- 自动重连**不得触发工具批准**（批准只在用户在场时做）—— 这条是 B 的**前提**，不是选项；
- 授权**可随时收回**，界面必须有一处能看见"哪些服务端开了自动重连"。

⇒ **R37 交付到"选项写清"为止；R47 所有者拍板 B；R52 按 B 落地**（§七）。

## 四、口径三：重连后正在跑的回合怎么办？

### 四.1 先说清一件事：**今天没有"自动重连"**

所以本节问的是**将来如果采纳了选项 B**，那条路径上正在跑的回合怎么办。
（选项 A 下没有"重连"这个动作，只有用户手动点"连接"。）

### 四.2 结论：**在跑的回合**不跟着重连走

**分开算两笔账**：

| | 处置 | 理由 |
|---|------|------|
| **已经在途的这一次工具调用** | **让它按自己的方式结束**（成功 / 超时 / 报错），**不重放** | 重放 = 副作用可能执行两次。本仓对"写文件 / 执行命令"的立场是**每次都要问过**（`run_command` 每次硬 ask）；**悄悄重放等于把一次批准变成两次执行**。 |
| **同一个回合后面的步骤** | **继续跑**，但**下一次用到该服务端工具时会拿到"不可用 + 为什么"** | 回合是模型的一次推理，不是"必须一次成功的事务"。工具失败会作为**工具结果**回到模型（`callTool` 返回 `{ok:false, text}`，`mcp-service.ts:482`），模型看得见并能决定怎么办。 |

### 四.3 一条现成的守卫可以直接用

`mcp-service.ts` 已经有一个 **generation 守卫**（`this.generationSeq += 1`，`:283`）：
每次 `connect` 都换一个 generation，**迟到的回调（旧连接的结果）不会污染新会话**。
`recordCallFailure` 里也已经有同一类检查（`:517` 的 `this.sessions.get(serverId) === session`）。

⇒ **将来若采纳 B，"重连"必须换 generation** —— 这条不是新发明，是**沿用现成的形状**。
（这也是本轮**不实现** B 的另一个理由：B 的正确性依赖这批并发时序守卫在**真并发**下被验过，
而那条路径**今天完全没有代码**。）

## 五、口径四：用户在哪里看得见？

### 五.1 今天已经看得见的（**不重复造**）

`McpPanel.tsx` 里每个服务端一行：

- **状态标签**（`STATE_LABEL`，`:16-23`）：`未连接 / 连接中 / 待你批准 / 已连接 / 失败 / 进程已退出`；
- **`lastError` 就在标题下那行**（`:230`）：`发现工具 N 个 · 已启用 M 个 · <lastError>`；
- **按钮随状态变**（`:239-252`）：`connected` / `awaiting_approval` 时是"断开"，其余是"连接"（`:251`）。

⇒ **掉线这件事今天就看得见**，不需要新界面。

### 五.2 但有一条**看不清**：为什么"失败"

`STATE_LABEL.error` 只有两个字"**失败**"（`McpPanel.tsx:21`），而 `lastError` 那行**只有服务端自己给的字符串**。
今天最常见的那条是 `callTool` 写回的"当前不可用（状态：error；上次失败：…）"——
**用户看到的是"失败"，但分不清是"服务端自己报错了"还是"它不应声了"**。

⇒ **口径（若将来动界面）**：`error` 必须能再分成**两种**（**与 R6c 那三类失败对齐**，不新造词汇）：

- **服务端自己说的**（`protocol` / `tool` 失败）⇒ 显示它给的原因，**服务端还活着**；
- **不应声**（`transport` 超时）⇒ 显示"**没等到回应**"，**服务端可能还活着但卡住了**。

**本轮不动界面**（这是"看得见"这题的**待办**，不是本轮的交付）。

### 五.3 "自动重连"若采纳，用户必须看得见三件事

1. **哪些服务端开了自动重连**（一个一眼能扫的标记）—— 否则"它怎么自己又起来了"就变成了惊吓；
2. **它试了几次**（"已重连 2 次" / "试了 3 次没成，已停"）—— 否则失败是静默的；
3. **重连时又批了什么**（工具批准**不复用**上一次 ⇒ 用户会看到新的一次批准）——
   这正是选项 B 免不掉的那一半，**必须让人看见**。

## 六、这一轮到底交付了什么、没交付什么

**R37 交付（可执行的口径）**：

1. **不设后台探活定时器**；"掉线"由**真实调用的失败**暴露，沿用 R6c 的三类失败分类；
2. **不设独立的"多久算掉线"阈值** —— 超时只由那次调用自己的 `requestTimeoutMs` 决定；
3. **`alive` 不是探活**（它只说"我 spawn 的 child 在不在"）—— 写进这一页，**不许拿它当探活用**；
4. **自动重连：结论是不做**（停牌①），**并把"若要做，该长什么样"的选项写清**（A / B + B 的五条边界）；
5. **将来若做：在途调用不重放**、回合继续跑、**重连必须换 generation**（沿用现成守卫）；
6. **看得见**：今天已看得见（状态标签 + `lastError` + 随状态变的按钮）；
   要补的是 **`error` 再分两种**（服务端自己说的 / 不应声）—— **本轮不动界面**。

**R37 没交付（明确划走）**：

- **自动重连的实现** —— 停牌①，等所有者拍板 A 还是 B；
- **界面把 `error` 细分** —— 待办，已写明形状；
- **周期探活的任何代码** —— 口径就是"不做"。

**这一页不改动任何判定语义**：`state` 的取值集合、`callTool` 的三道校验、
`recordCallFailure` 的分流、`handleExit` 的行为 —— **一行都没动**。
R37 的产物是**一页文档**，外加台账与队列的改口。

### 七.3 掉线怎么被认出来（**仍然不是被"测"出来的**）

自动重连只从两个**既有事实**触发，**没有新增任何探活或定时器**：

- **进程真的退了**（`handleExit` 的现成回调）；
- **一次调用什么都没等到**（`recordCallFailure` 里 `failure === 'transport'` 的现成分流）。

`alive` **没有被当探活用**（§一.2 已写死它不是探活）。服务端自己回了错（`protocol` / `tool`）
**不触发**重连 —— 那种情况证明它还在说话。

### 七.4 那个最容易埋雷的地方：重连时的那次 `disconnect` 会不会杀掉用户正在用的连接

**结论：不会。** 三道闸叠着（详见本轮报告 §3）：

1. **只断自己那条**（`onlySession` 身份闸）—— 自动重连只准断它自己发起时看到的那条会话；
   若表里那条已经换了人（用户刚自己连过），**直接让位，一个进程都不起**；
2. **用户点「连接」先撤掉排队的重连** —— 不存在"用户刚点完，两秒后自动重连又来一遍"；
3. **断的过程中用户又点了 ⇒ 让位**（用户意图序号）—— 不去覆盖用户那条。
